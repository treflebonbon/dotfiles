## apm 管理の外部 skill

`apm.yml` / `apm.lock.yaml` が外部 skill を `~/.claude/skills/` へ展開する。lockfile の再生成は下記「APM lock の生成」の手順に従う（`apm lock` 単体では不十分）。配備は `apm install --frozen` が `run_onchange_after_apm-install.sh.tmpl` から冪等に走る。

**mattpocock 設計→実装ワークフロー** (`mattpocock/skills/skills/engineering/`)。公式27 skillを exact revision `a496f5513d4a4cf889bc48e189e579f4b0bdf6aa`（上流 plugin manifest version `1.3.2`）から APM で配備する。公式セットと標準workflowは [ADR-0071](../docs/adr/0071-adopt-mattpocock-standard-workflow.md) に従い、`ask-matt` の案内更新は [検証記録](../docs/research/update-mattpocock-20261005.md)、wizard更新の採用は [検証記録](../docs/research/mattpocock-pr-20261013.md)、1.3.2のfresh context案内などの採用は [2026-10-31の更新記録](../docs/research/update-tools-skills-20261031.md) を参照する。Matt の `package_type` は APM の native 出力に従い、lock の更新経路によって `apm_package` と `marketplace_plugin` の間で変わる（2026-10-09 の native lock は `marketplace_plugin`）。どちらも pin・selected payload・配備 ledger は同じで、手で書き換えない。

_User-invoked_（明示起動のみ、orchestration 層。メインフロー1本 + on-ramp 2つで構成する — 詳細は [ADR-0014](../docs/adr/0014-triage-not-after-to-issues.md)、上流 `ask-matt` の main-flow/on-ramp 構造に整合）:

- メインフロー: native worktree での作業開始 → `grill-with-docs` → `to-spec` → `to-tickets` → `implement-spec`（仕様全体）または `implement`（個別 ticket）。小さな要件確定済みの作業は `implement` から直接入る。PR 本文は model-invoked の `pr`、実装後の振り返りは user-invoked の `retro` を使う。`tdd` の green slice commit・`code-review` 後の修正 commit は実装依頼の範囲で確認なしに行う。`implement` が ready-for-agent の ticket を入力とする場合に限り、`tdd` はその受入条件からテストする公開境界（seam）が一意に導けるとき、それを合意済みの seam とみなしてユーザー確認を省く（[ADR-0019](../docs/adr/0019-builder-evaluator-cross-issue-autonomy.md) §4）。ticket を経由しない直接起動、受入条件がない、または境界が曖昧な場合は `tdd` どおり確認する（vendored skill 本体は改変しない）。`code-review` は `git diff <fixed-point>...HEAD` の commit 済み差分を対象にし、empty diff は fail する。
- on-ramp（raw issue: `to-tickets` の産出物には使わない）: `triage` → ready-for-agent 化 → `implement` へ合流
- on-ramp（ハードなバグ）: `diagnosing-bugs` → `code-review`。PR 本文は `pr`。raw な報告ならまず `triage` を通す

外部 skill は APM 配布物を fork せず、repo の指示層で必要な差分だけを **ローカル skill 上書き**として定義する（[ADR-0023](../docs/adr/0023-resolve-external-skill-contracts-locally.md)）。現行の上書き:

- `ask-matt` は現在の依頼と合意済みの完了範囲から次の手順を選ぶ。別 repo への導入など、対象・利用希望が未確定の作業は任意と明示する。
- `handoff` は作成前に [引継ぎ対象の照合](../docs/conventions.md#引継ぎ対象の照合) を実行し、root・branch・HEAD・PR の照合結果と記録先を文書へ含める。不一致・未作成・照合不能を区別し、ユーザーが指定したローカルの検証対象を明記する。
- `triage` は推薦根拠を得る read-only 検証を推薦前に実行してよい。推薦・適用内容の判断点は維持するが、内容確定後の非破壊な GitHub 定型書込みは二重確認しない。reopen/delete は引き続き確認する（GitHub app 経由の reopen を除く）。
- `triage` が投稿するコメントの冒頭ディスクレーマー（`This was generated by AI during triage.`）は、上流の固定文を英語のまま使う。コメント本文は日本語で書く。
- `pr` は peer 協働の PR 本文に元候補・受入条件と検証結果・非目標・Decisions を含め、issue がある場合だけ `Closes #N` を付ける（[autonomous-peer-contract](autonomous-peer-contract.md)）。
- `improve-codebase-architecture` は候補提示前に、実 caller の知識が既存 module interface から減り、削除テストでその module の有用性が増す具体的根拠を確認する。caller 数は足切りにせず、sole caller でも根拠があれば候補にできる。根拠のない案と helper 整備・単なる移動だけの案は数合わせに採らない。該当候補がなければ Top recommendation を「該当候補なし」とし、候補選択質問をせず、調査 scope と却下理由を日本語 report に記録して正常完了する。候補が存在しても peer 依頼が未承認のまま未選択なら、その状態を記録して pin・peer-refactor を起動しない。ユーザーが独立検証を明示依頼した場合は妨げない。
- `improve-codebase-architecture` の report が挙動を「バグ」や「非一貫」と断定する前に、その挙動を固定する既存テストと上流の正規化を読み、正規化後にも反例が残るかを確認する。sub-agent の報告は未検証の主張として扱う。既存テストがあるだけで正しい挙動とは判定しない。
- `improve-codebase-architecture` の提示済み候補について人が peer 協働による改善を明示依頼した場合、Orca では固定 plugin の `orca-peer-refactor` を使う。`herdr-peer-refactor` も公開 plugin に保持されるが、Herdr TUI 専用であり App 対応ではない。TUI を別途利用する明示依頼がない限り選ばない。どちらも人が選んだ候補と既存承認を引き継ぎ、上流 skill の探索と `grilling` は fork せず変更しない（[契約](autonomous-peer-contract.md)、[ADR-0075](../docs/adr/0075-adopt-peer-refactor-skills.md)）。
- `improve-codebase-architecture` の HTML report は固定 plugin source の該当 skill script で構造を検査し、実ブラウザで描画を確認してから提示する。`herdr-peer-refactor` は TUI 専用、`orca-peer-refactor` は Orca 専用である。source path の解決と Mermaid 検査契約は [autonomous-peer-contract](autonomous-peer-contract.md) を参照する。
- Herdr App の terminal と `hc` は [AI runtime guide](ai-runtimes.md#windows-herdr-app-と-wsl2-core) に従う。公開 `herdr-peer-refactor` skill は TUI 専用であり、App の起動・協働手順として案内しない。
- `find-skills` はインストール手順として `npx skills add -g -y` を案内するが、外部 skill は `apm.yml` / `apm.lock.yaml` 経由でのみ導入する。このコマンドは実行せず、追加候補は `apm.yml` への追記として提示する。
- `pdf` の SKILL.md は `REFERENCE.md` / `FORMS.md` を指すが、実ファイルは小文字の `reference.md` / `forms.md`。小文字のファイルを読む。
- `wizard` に書く CLI コマンドは、書く前に `--help` で対話プロンプトと設定ファイルの自動更新の有無を確かめ、それを止めるフラグを付ける（例: `wrangler r2 bucket create` には `--update-config=false`。付けないと、バインディングを設定へ追加するかを尋ね、了承すると repo の設定ファイルを書き換える）。人が wizard を実行し終えたら、`git status` と `git diff` を実行前と比べ、想定外のファイル変更が無いことを確かめる。
- Builder-Evaluator 内の `code-review` は branch の既知の base（通常 `origin/main`）を fixed point として自動採用してよい。standalone で fixed point が不明な場合だけ質問する。
- `code-review` の Spec 軸には、ユーザーが承認した要件原文と後続の修正・追加、実装上の判断、過去の参考記録を区別して渡す。制約の根拠は現在の依頼に照合し、要件違反の指摘には原文または現在適用される仕様の箇所を示す。過去資料や agent の提案を現在の制約として扱う場合は、その採用根拠を明記する。
- dotfilesのツール・スキル更新を `code-review` する場合は、[更新の追跡とレビュー](../docs/conventions.md#ツールスキル更新の追跡とレビュー)に従い、両軸へ現在の要件・適用ADRの箇所・予定変更と分割時に外した変更の調査記録を渡す。
- `gh-address-comments` は GitHub plugin の flat な comment read と `gh api graphql` を併用せず、thread-aware な取得・返信・resolve を専用 CLI `gh-review-thread` に統一する。review 対応依頼は選択 thread 群の Review Round（修正・検証・`fix: address PR review feedback` commit・`git-push-topic`・日本語返信・resolve）を承認する。コード修正は commit が現在の PR 履歴に含まれた後だけ短縮 SHA・修正要約・検証結果を返信して resolve する。説明のみは `--explanation-only` を明示し、根拠を返信して空 commit を作らない。同一本文の自分の返信は再投稿せず未完了の resolve から再開し、thread 単位の失敗は open のまま理由を記録して残りを続行する（[ADR-0032](../docs/adr/0032-automate-review-round.md)）。bot の本文は `inspect --plain` で既知の HTML・バッジを除いて読み、手書きのタグ除去はしない。実機の挙動に関する主張（返信・PR 本文を含む）には confirmed（この session で確認）／inferred（部分的な証拠からの推論）／unconfirmed（未確認）を付ける。
- `empirical-prompt-tuning` は `tool_uses` または `duration_ms` を取得できない round を strict convergence の判定に含めない。`qualitative plateau; quantitative convergence unverified` と報告して metadata を提供する runtime で再評価するか、明示的な `resource cutoff` として終了する。

### Managed workflow semantics と local safety boundary

採用 revision の workflow 本文は、skill を fork せず APM payload とこの指示層の組み合わせで採用する。

- **Explicit invocation**: cross-skill 呼出しは `Call the Skill tool with "<name>"` 相当として Skill tool と skill 名を明示する。setup 情報がなければ、依存する skill は user-invoked の `setup-matt-pocock-skills` を自動実行せず、ユーザーへ明示起動を案内する。
- **Frontier grilling**: `grilling` は依存関係が解決済みの全 decision を frontier round でまとめて提示し、各質問へ推奨を添え、複数質問の間を horizontal rule (`---`) で区切る。各 round の人間の回答を待ち、事実は環境探索で埋め、未回答の decision を推測して先へ進まない。`ui-grill-with-docs` は同じ frontier round の全質問をラウンド質問シートにまとめ、visual comparison が必要な質問には同じHTML内で disposable mockup を添える。回答はMarkdownでコピーしてチャットへ渡す。
- **Phase boundary**: 公式の選択肢は `Continue → /clear → /handoff → Subagent → /compact`。phase の途中では判断せず、boundary でこの順に評価する。次 phase が現 phase を primary source として必要、または smart zone（目安 ~150k tokens）に収まるなら `Continue`。context が次 phase と無関係なら `/clear`。新しい harness / directory / repo / colleague へ portability が必要な場合だけ `/handoff`。AFK で独立して実行できる scoped task は `Subagent`。同じ harness / directory の relevant context を保ったまま要約する場合は `/compact` を使う。
- **一括実装**: `implement-spec` は ticket graph の実行可能な frontier を専用 worktree の implementer subagent へ並列に割り当てる。成果物を一つの Integration Branch へ集約し、全 ticket の完了後に `code-review` と修正を行う。GitHub では最初の集約後に spec と対象 ticket を closing reference にした draft PR を作り、全実装・レビュー・修正後に ready 化する。明示的な `implement-spec` 呼出しは、この draft 作成・topic push・PR 更新・ready 化を依頼範囲で承認する。GitHub の issue close は PR merge 時に行い、merge 前に実装側から直接 close しない（ユーザーが依頼した close は確認不要）。
- **Model-invoked safety**: model-invoked discipline は current repository の実装契約内で動くが、外部書込み（Issue / PR / shared service など）は親の Contract または明示的に起動された user-invoked skill の承認範囲に限る。機密情報・credential・CI secret は読み出し、出力、commit、無断変更をしない。新しく作る値も同じで、ユーザーに実行を案内するコマンドでも画面・会話・ログに出さない。承認された登録先へパイプで渡すか権限 0600 の一時ファイルを経由し、人の操作が要る部分だけ `wizard` を使い、登録は値を読み戻さず成否で確かめる。権限拡大や permission bypass は推測せず、現在の runtime profile と project instructions に従い、必要ならユーザーへ戻す。
- **Prototype lifecycle**: state model を検証する `prototype` の logic path は single self-contained HTML とし、build / server 不要、inline の pure logic、free-play と guided walkthroughs、各操作後の全 state 表示を持つ。決定を本実装へ反映した後も prototype 全体は throwaway branch に primary source として残し、implementation issue から参照する。main branch には検証済み decision だけを残す。
- **Instruction ownership**: 全 repo 共通の指示は Claude Code 向けの `~/.claude/CLAUDE.md` と Codex 向けの `$CODEX_HOME/AGENTS.md` に別管理する。共有すべき workflow / safety contract は双方で整合させ、runtime-specific な browser / tool 差分は各ファイルに残す。OpenCode / Zed / Cursor などのグローバル指示はこの dotfiles では管理しない（[ADR-0078](../docs/adr/0078-keep-repo-instructions-out-of-home.md)）。
- **Worktree ownership**: integration と各 implementer の worktree 作成・選択は native 機構へ委ね、開始時の検証と参照不能時の復旧は下記「Worktree の開始と復旧」に従う。子は開始時に Integration Branch を base とすることを確認する。上流の reset／cleanup 指示は破壊操作の承認ではない。誤った base の破壊的 reset と worktree 削除は対象を明示して確認し、未コミット変更・失敗した作業を保持する。

### PR 公開

`pr` は本文作成を担当し、公開はユーザーの依頼または `implement-spec` の承認範囲で行う。本文は上流の変更概要・変更前後の証拠・merge の危険性を日本語で記述し、図は Mermaid、タイトルは英語の Conventional Commits にする。検証には実装で得た結果を使い、未確認事項を明記する。

実際の remote default branch を `git ls-remote --symref origin HEAD` で解決し、topic branch を `git-push-topic` で公開する。本文は新しい一時ファイルへ書き、`gh pr create --base <default-branch> --title <title> --body-file <file>`、既存 PR は `gh pr edit --body-file <file>` を使う。実装依頼だけで PR 公開を自動追加せず、force push・default branch への直接 push・PR merge は既存規則に従う。

dotfiles の公開補助入口は `scripts/publish-topic.py`。pushと読取り専用の確認を分け、確認待ちからの再開でpushを繰り返さない。認証selectorの引継ぎと記録の扱いは [公開手順](../docs/conventions.md#topic-branch-の公開と確認)を読む。

### 検証用の実行境界

Linux／WSL2 の検証コマンドは、task worktree の `scripts/verification_env.py SOURCE -- COMMAND...` から開始する。Nix・commit hook・全 Bats を伴う検証は `scripts/verify-ai-tools.py` が同じ書込み境界を最初の Nix 評価から適用する。通常 HOME を read-only にし、ホスト側では対象 task worktree・Git metadata・`/tmp/codex` だけへ書き込める。例外として `--managed-browser` を明示した場合だけ、共通の Managed Chrome 所有権記録へも書き込め、ホストの PID namespace を使うため同じ利用者のホスト process を参照・signal できる（[ADR-0085](../docs/adr/0085-share-managed-chrome-ownership-in-verification.md)）。`/tmp` の固定利用には namespace 内の専用 tmpfs を与える。条件不足や起動失敗は停止し、無保護の実行へ切り替えない。使い方と実 CLI の受入チェックは [検証手順](../docs/conventions.md#テスト)を読む。

canonical検証の準備から始める場合は `scripts/run-canonical.py` を使い、既存の検証本体へつなぐ。導入済みImpeccable hookが必要で、最初のNix評価から同じ境界を適用する。

書込み保護を要求する Codex 検証セッションは、native に作成済みの task worktree から既存の `codex-worktree` で起動する。公開入力の登録・trust・モデル接続・結果返却は [raw Codex の隔離入口](shell-environment.md#raw-codex-のプロジェクト開発環境)に従う。既存セッションへ隔離を後付けしない。Claude／Antigravity の対話セッションを保護する起動経路は今回の対象外で、認証方式を含め別に設計する。

### Worktree の開始と復旧

検証コマンドや検証用 Codex を起動する前に、前節「検証用の実行境界」の入口を選ぶ。

Worktree Entry Point は、対象 task worktree を確認して作業を始める契約。独立スキルの呼出しは不要。作成・選択には実行環境の native 機構を使い、既存の task worktree は同じ依頼への所属を確認して再利用する。変更前に `git fetch origin` し、physical root、ブランチ、HEAD（`origin/<default>` との一致を含む。native 作成は fetch 前の古い参照から作ることがある）、status、worktree 固有 Git dir と common dir を read-only に確認し、全 phase を同じ checkout で続ける。既存の branch を再利用するときは、その branch の PR が merge 済みでないかを `gh pr list --head <branch> --state all --json number,state,headRefName` で確認し、状態を文字で読む。MERGED なら squash 後の履歴は branch と一致せず、`git-push-topic` も拒否するため、積まずに `origin/<default>` から新しい branch を切り、必要な commit だけを持ち込む。隔離内の `gh pr list` は `--head` を拒否し、`--state` も受けず、open な PR しか返さないため、この確認は隔離の起動前にホストで済ませる。新しい branch が要るときは、その branch で GitHub policy を登録してから起動する。policy は1 topic に固定されるので、隔離 session の途中では branch を切り替えない。GitHub を使えないローカル作業では、この確認を公開前まで延期できる。親の未コミット変更を移動・上書きしない。説明・読み取り調査は primary checkout や Git 検証不能の環境でも継続できる。

- **Herdr App**: connected machine の standard worktree を App から開き、validated linked worktree の terminal で `codex-worktree` または `codex-reviewer` を起動する。`--no-daemon` と親側の `hc` orchestration を含む詳細は [AI runtime guide](ai-runtimes.md#windows-herdr-app-と-wsl2-core) を参照する。
- **Orca**: native worktree と Agent Picker の built-in agent 起動を使い、permission mode は Orca に委ねる。自律 workflow は shipped Yolo、確認を残す場合は Manual と Orca Source Control を使う。Orca native Codex は `codex-orca` / `codex-worktree` を使わない。worktree は review / recovery の境界であり OS sandbox ではないため、Yolo は信頼できる repository / host に限る。runtime 自己認識で Orca を識別し、`ORCA_*` environment の汎用判定は導入しない。Orca primary checkout からの実装は native worktree の新しい agent session で開始する。
- **読み取り専用レビュー役の Codex**: App/core terminal では validated linked worktree を cwd にした shell から `codex-reviewer --no-daemon [codex の引数]` で起動する。通常の明示協働では `codex-reviewer --peer`（`dotfiles-peer` profile）を使う。専用 peer auto は固定 public source の明示 preflight と起動 wrapper に限り、`herdr-peer-refactor` の TUI-only flow を App へ当てはめない。通常 reviewer は対象 worktree の Git dir と Git common dir を read だけで加えるので、Git 書込みや別 worktree は扱えず、raw 実装役と同じ秘密隔離も提供しない（[ADR-0080](../docs/adr/0080-grant-reviewer-codex-read-only-git-metadata.md)）。
- **Claude Code / Codex**: Claude Code は `EnterWorktree`、Codex app は native worktree、Codex CLI の新規作成は導入版の `codex --help` に従い `--worktree` を使う。native 作成と隔離起動は別の責務。raw Codex の秘密隔離が必要な場合は、作成済み linked worktree で既存 `codex-worktree` を使い、その公開入力登録・trust・返却契約に従う。

ローカル変更につながる診断・実装を Orca の Git task worktree で監督する場合は、着手前に固定版 public source の `skills/orca-peer-refactor/references/orca.md#worktree-readiness` を確認します。source root は [契約案内](autonomous-peer-contract.md) にある検証済み plugin JSON の `source` から解決し、worker 観測と割当時に固定した期待値の照合成功を待ちます。同じ実行 host の worktree 検証が前提で、remote placement は実行 host 側の独立観測を要します。folder workspace、および primary checkout での説明・状態確認・読み取り調査は対象外です。

Orca で親による監督（完了追跡・質問応答・decision gate）が依頼された場合は既存の `orchestration` skill を使い、通常の端末操作と監督を伴わない所有権移譲には `orca-cli` を使う。具体的なコマンドと現行 API は利用中バイナリの `skills get orchestration` が返す version-matched guide を正本とし、上流 guide をここへ複製しない。worker/coordinator が複数行または shell 記号を含む `status` / `dispatch` 本文を送る場合は、配備された `orca-send`（source: `private_dot_local/bin/executable_orca-send.tmpl`、target: `~/.local/bin/orca-send`）へ `--cli <選択済み Orca 実行ファイル> --body-file <UTF-8本文ファイル> -- <native send 引数>` を渡す。これは選択済み CLI の `orchestration send --body <本文> ...` を shell なしで呼ぶ入口で、native ID・権限・送信結果の契約を保つ。本文のサイズ上限と argv 露出の制約は `skills/orca-peer-refactor/references/orca.md#literal-message-body` に従う。親は Task / Dispatch で担当試行を識別し、`send` の成功は永続的なキュー登録だけを示すものとして受信・着手とは区別する。`worker_done` は期待する Task / Dispatch と検証証拠を照合してから処理・ack し、応答が不明な場合は同じ試行を調べて guide の既存復旧手順に従う。**ローカル変更につながる診断・実装を Orca の Git task worktree で監督する場合は、着手前に `skills/orca-peer-refactor/references/orca.md#worktree-readiness`（固定版 source は [契約案内](autonomous-peer-contract.md) の JSON `source` から解決する）を行い、worker 観測と割当時に固定した期待値の照合成功を待つ。同じ実行 host の worktree 検証が前提で、remote placement は実行 host 側の独立観測を要する。folder workspace、および primary checkout での説明・状態確認・読み取り調査は対象外。**

merge を確認した task worktree の片付けは、削除の依頼があるときに限り、native 機構で行う。Orca では `orca-cli` の解決規則で選んだ実行ファイル(Orca 端末では `$ORCA_CLI_COMMAND`)の `worktree rm --worktree <selector>` を使い、selector は対象 PR の branch または HEAD と一致することを確認した worktree の完全な id(`id:<repoId>::<path>`)で明示する。primary checkout からの raw `git worktree remove` は使わない。削除前に PR の merge、未コミット変更と未 push の commit が無いこと、担当 agent の停止を確認する。実行ファイルが使えない、または権限が足りないときは削除せず、未削除として依頼元へ戻す。force 削除とブランチ削除はこの手順に含めず、別に確認する。

Git 管理情報を解決できない場合は編集・Git 書込みを保留し、以下を区別する。

1. **owner 側でも検証不能**: pointer / back-pointer / common dir の不整合、参照先消失、別 repository への所属を読み取りで診断する。変更を始めず、確認できた原因と必要な修復を報告する。
2. **owner 側では有効、子から参照不能**: worktree の破損とは断定せず、実行環境の参照範囲を調べる。親は同じ worktree に正規経路の後継セッションを起動し、依頼・合意・対象 root / branch / HEAD・変更状況・実施済み検証・残作業を引き継ぐ。子が自分の環境で再検証に成功してから変更を再開する。親の検証だけで子の検証を省略しない。

依頼済みタスクの正規経路での復旧・引継ぎには二重確認を求めない。後継起動前に元担当が編集を停止していることを確認し、同じ worktree を同時編集しない。既存 pane の強制終了、worktree の削除・作り直し、権限拒否の迂回、共有設定の権限拡大は復旧に含めない。新しい根拠や正規経路がない同じ失敗は繰り返さず、最後の検証結果と再開に不足する条件を報告する。

Herdr TUI 0.9.0 adapter の agent 認識失敗は [ADR-0057](../docs/adr/0057-retire-to-worktree-for-native-entry.md) の歴史記録であり、App/core の agent 状態を示す根拠には使わない。App の応答完了は [AI runtime guide](ai-runtimes.md#windows-herdr-app-と-wsl2-core) の `hc wait` / `hc read` 条件で確認する。

起動しただけでは引継ぎ完了としない。対話 agent の認識・入力可能状態と、子からの checkout / Git 検証を別々に確認する。`codex-worktree sandbox` の成功は対話 agent 起動の代用にならない。配備済み公開入力・trust・接続前提が不足している場合も、通常環境の秘密値や権限を変更して代用しない。

raw adapter の model 指定は既存の `--model`／`-m`、effort 指定は `-c 'model_reasoning_effort="xhigh"'` を使う。effort は `-c VALUE`／`--config VALUE`／`--config=VALUE`／`-cVALUE` の一回だけを許可する。VALUE は裸キー `model_reasoning_effort` と空でない TOML string の代入に限る。引用キー、別キー・追加キー、未引用の値、重複指定、`-c=VALUE` は起動前に拒否する。省略時は既存 managed config に従う。文字列の復号・境界例は [入力契約](../docs/research/codex-model-effort-contract-20261009.md#cli-入力) を参照する。

app-server で実タスクを引き継ぐ親は、同じ隔離 process/thread で次の gate を満たす。これは親の workflow 手順であり、adapter が自動強制する機能ではない。

1. 対象 checkout の Git 所属を検証し、`thread/start` の model と `config.model_reasoning_effort` を指定する。応答の thread ID、model、reasoningEffort、modelProvider、cwd を記録し、指定値・対象 root・隔離 provider と照合する。
2. 同じ thread へ読み取りだけの readiness turn を送り、root／branch／HEAD／Git dir／common dir の一致、実応答、`turn/completed` の成功を確認する。
3. 起動 stderr の隔離 session directory の `config/sessions/` から、その thread ID の rollout を選び、`turn_context` の model／effort／cwd だけを抽出して照合する。effort は TOML の復号値で比較する。hidden reasoning・認証情報は抽出しない。
4. 一致後に同じ process/thread へ実タスクを送る。`turn/start` の model／effort は省略または readiness と同じ値とする。不一致・観測不能・未対応なら送らず、設定を黙って下げない。設定変更、thread／process の変更・resume 後は readiness と記録確認をやり直す。

CLI の model／effort 指定は利用できるが、CLI 自動引継ぎは未対応。同じ隔離 process/thread の有効値観測と readiness からの継続を確認するまで対応済みとしない。別 raw 起動の `exec resume` は過去の rollout を持ち込まないため、この gate の継続経路に使わない。確認は runtime 設定とモデル応答までで、バックエンドの実際の推論計算量は保証しない。

- wayfinding: 巨大で曖昧な作業は `wayfinder` で調査・決定 ticket の map を作り、frontier が明確になってから Planner / Builder-Evaluator へ合流する

`ready-for-agent` ラベルを付与する際は、`triage` 経由・`to-tickets` 経由のいずれでも次の6項目を最低条件とする: 目的 / AC / 非目標 / 検証方法 / 関連ファイル・入口 / 判断済み tradeoff（[GLOSSARY.md](../GLOSSARY.md) の Contract 参照）。`triage` / `to-tickets` はいずれも apm 経由の vendored skill であり、この最低条件を skill 自体に組み込んで機械的にゲートすることはできない——ラベルを付与する運用者（実行エージェント自身）が確認する doc-level discipline とする。2つの経路でチェックポイントの位置は異なる: `triage` は「Apply the outcome」というラベル付与前の明示的な判断点を持つため、そこで6項目の充足と規約照合を確認してから `ready-for-agent` を付与する。`to-tickets` は ticket の生成とラベル付与を同一ステップ（Publish the tickets）で完結させ、付与前に立ち止まる地点が無いため、事前ゲートではなく**生成直後**に各 ticket 本文を確認し、6項目のうち ticket 本文から読み取れないものがあればその場で本文に追記する（[ADR-0015](../docs/adr/0015-add-tdd-commit-confirmation.md) の commit 確認ステップと同型のタイミング配慮）。

6項目に加えて、規約との照合も最低条件とする。AC と判断済み tradeoff に出てくる環境変数・資源名・パスを `docs/`（`docs/research/` の調査記録を除く）と `runtime/` で検索し、矛盾する規約が見つかったら、issue に「規約の変更または例外」を明記するか、`needs-info` に戻す。照合範囲はこの固有名詞に絞り、全規約は読ませない（判断が要るため機械的な検出は設けない）。位置は上記の2経路に合わせ、`triage` では「Apply the outcome」の前、`to-tickets` では生成直後に行う。`to-tickets` ではすでに `ready-for-agent` が付いているため、「戻す」は `ready-for-agent` を外して `needs-info` を付ける操作を指す。

- `setup-matt-pocock-skills` — **必須エントリポイント**。per-repo で issue tracker（GitHub / GitLab / local markdown / その他）、triage label 語彙、domain doc レイアウト（`GLOSSARY.md` + `docs/adr/`）を構成し `docs/agents/*.md` を生成
- `grill-with-docs` — 対話しつつ `GLOSSARY.md` と ADR を更新（`domain-modeling` に委譲）
- `to-spec` — 会話を spec（旧称 PRD）にして issue tracker へ publish
- `to-tickets` — plan/spec を vertical slice の ticket に分解
- `implement` — spec/ticket に基づく実装入口。可能な範囲で `tdd` を使い、最後に `code-review` して current branch に commit
- `triage` — issue を state machine（needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix）で捌く
- `ask-matt` — user-invoked skills の router（どのフローが合うか迷った時）
- `improve-codebase-architecture` — ball-of-mud レスキュー。deepening 機会を HTML レポートで提示
- `wayfinder` — 1セッションに収まらない巨大で曖昧な作業を、調査・決定 ticket の map と frontier に分解

- `implement-spec` — spec と ticket graph 全体の並列実装を一つの Integration Branch へ集約
- `retro` — current または指定セッションから環境改善案を提示

_Model-invoked_（実装フェーズで自動発火する discipline 層。上流ルール: user-invoked は他の user-invoked を呼ばない）:

- `tdd` — red-green-refactor
- `pr` — 変更概要・変更前後の証拠・merge の危険性を示す PR 本文
- `code-review` — Standards 軸 + Spec 軸の 2 軸並列レビュー
- `diagnosing-bugs` — ハードバグ / 性能回帰の診断ループ
- `domain-modeling` — `grill-with-docs` / `triage` が委譲する依存（`GLOSSARY.md` + ADR 維持の実体）
- `codebase-design` — deep module 設計の共有語彙（interface / seam / testability）
- `prototype` — 設計質問に答える捨てプロトタイプ
- `research` — 一次情報リサーチを background agent で行い cited Markdown を残す

個別実装の user-invoked entrypoint は `implement`、仕様全体の一括実装は `implement-spec`。`tdd` / `code-review` / `diagnosing-bugs` は model-invoked discipline として必要時に発火する。`pr` は PR 本文作成時の model-invoked skill、`retro` はセッションを振り返る user-invoked skill で、指定がなければ現在のセッションを対象に環境改善を提案する。

このワークフローは per-repo で完結する。ラベル provisioning は dotfiles では持たず、各 repo で `gh label create` または skill のランタイム挙動に任せる。domain doc は mattpocock ネイティブの `GLOSSARY.md`/`docs/adr` を使い、この `runtime/` バンドルとは混ぜない（`runtime/` は home-wide ambient 知識専用）。

### APM のマルチランタイム配布

`apm.yml` の `targets` は `claude` / `codex`（apm の `install` は `antigravity` target を非対応）。apm は全 skill を APM-native の共有ハブ `~/.agents/skills/` に必ず materialize し（target とは独立）、Claude 向けには `~/.claude/skills/` にも配備する。**Codex は `~/.agents/skills/` を global skills location として直接読む**（`codex debug prompt-input` による実機確認記録は [ADR-0040](../docs/adr/0040-adopt-mattpocock-v1-2-3-full-set.md)）。`~/.codex/skills/` は Codex の native location だが、このmanifestが選ぶAPMの配備先は共有ハブであり、過去に配備された real dir が残っていても discovery は `~/.agents/skills/` 側が担う。

Antigravity の公式 global skills location は `~/.gemini/config/skills/`、workspace 向けは `<workspace-root>/.agents/skills/` である（[公式ガイド](https://antigravity.google/docs/skills?app=cli#cli-skill-locations)）。この repo の採用版が共有ハブ `~/.agents/skills/` を global に discovery するかは未確認（unconfirmed）。APM skill の Antigravity での可視性は、採用版での discovery 確認後に判断する。

### APM lock の生成

apm の target 解決はカレントディレクトリ基準なので、validated task worktreeのsource外にcwd／HOME／XDG directoryを隔離し、候補の`apm.yml`をコピーする。通常APM・Impeccableの候補生成とMatt gate後のnative lock採用は、そのcwdで`"$SOURCE_DIR/scripts/generate-apm-lock.sh" "$SOURCE_DIR"`を実行する。共通コマンドはsourceのNix snapshotが選ぶAPM版と実CLI版を生成前に照合し、live onchangeと同じ`apm install --target claude,codex --https`で生成したlockの`apm_version`を生成後に照合する。既存lockの生成版を期待値に使わない。不一致・欠落・判定失敗はそこで中止し、候補runtimeとログを証拠として保持する。失敗したlockをsourceへコピーせず、後続のfrozen／auditにも進まない。この照合は候補生成時だけに適用し、snapshot先行merge後のHOME配備にCLI版と既存lock版の一致を要求しない。

installが新規配備時にdeployed_files / deployed_file_hashesをlockへ追記するため、`apm lock`だけのlockを採用するとmaterialization情報が欠落する。共通コマンドが成功したら同じ隔離環境で`apm install --frozen --target claude,codex --https`前後のlock SHA-256不変と`apm audit --ci`を確認し、対象payloadの検証も終えてからlockをsourceへ戻す。非candidate dependencyを一時pinするupdate gateの作業用lockをそのままsourceに採用せず、最終source lockは実際のunpinned manifestから生成されたnative形式（`resolved_ref`はmanifestのexact pinだけ、single-quote）にする。`~/.agents/skills` / `~/.claude/skills`は直接変更せず、lockはoxfmtで再整形しない（`lefthook.yml`で除外済み。再整形するとapmがruntimeで書き戻してchezmoiと永続driftする）。

### APM の配備比較

上記の生成・frozen no-rewrite・audit を通過した隔離 runtime で、validated source 内の手動 helper `scripts/verify-apm-deployment.mjs` を使う。`SOURCE_DIR` はその checkout、`BASE_LOCK` は更新前の accepted lock、`CANDIDATE_RUNTIME` は候補 lock と両 target の配備先を持つ directory とする。

```bash
bun "$SOURCE_DIR/scripts/verify-apm-deployment.mjs" \
  "$BASE_LOCK" "$CANDIDATE_RUNTIME" "$PLAN_JSON"
```

`PLAN_JSON` の下書きは `bun "$SOURCE_DIR/scripts/plan-apm-deployment.mjs" "$BASE_LOCK" "$CANDIDATE_RUNTIME/apm.lock.yaml"` が標準出力へ出す。floating の `resolved_commit` だけが進んだ dependency を除き、いずれかの field が変わった dependency（`content_hash` だけの変更を含む）を候補に挙げ、追加・削除は `deployed_files` の差分から作る。候補にする判断は人が確認し、生成結果をそのまま採用しない。

`PLAN_JSON` は配列そのものではなく、次の形式の object にする。これは形式例であり、`repo_url`／`virtual_path` は native lock と一致させ、directory を含む `deployed_files` の追加・削除を事前に列挙する。

```json
{
  "candidates": [
    {
      "repo_url": "googlechrome/modern-web-guidance",
      "virtual_path": "skills/modern-web-guidance",
      "added": [
        ".agents/skills/modern-web-guidance/guides/forms/slider.md",
        ".claude/skills/modern-web-guidance/guides/forms/slider.md"
      ],
      "removed": []
    }
  ]
}
```

helper は既存 dependency の更新と計画済みの dependency 削除を扱い、新規 dependency の追加と予定外の削除を拒否する。dependency 全体を削除する計画は追加0・旧配備 file 全件の削除を要求し、他 owner が保持する file を除いて配備先から消えたことも確認する。候補の追加・削除の完全一致、全配備 file の実 bytes／hash、runtime 外への path／symlink の拒否、両 target の skill discovery、`SKILL.md` の `name`／`description` frontmatter を検査する。guide Markdown には SKILL 用 frontmatter を要求しない。候補外 dependency は全 metadata を不変とし、更新前に `ref`／`resolved_ref` がない floating dependency の `resolved_commit` だけの変更を許容する。計画に含めた候補の revision／content／その他 metadata の更新は比較から外れるため、期待する pin／版／package type は manifest・native 生成・audit と当該更新 gate で別途照合する。

隔離runtimeの比較では、root lock metadata、`deployments` の owner／active_owner／共有 owner ledger の前後比較、payload の意味、未記録 file 全体の列挙、対話 loader は helper の検査範囲外とする。既存の生成・frozen・audit と候補外／共有 owner ledger の独立比較を継続し、helper の PASS だけで全 lock 不変や配備完了とは判定しない。既存 frozen runtime の再利用では source の manifest／lock との byte 一致を先に確認し、`{"candidates":[]}` で追加・削除0を照合する。helper は native lock を読み取るだけで、HOME へ配備せず、既存 runner／hook／下記 Matt 専用 gate へ自動配線しない。

### APM dependency 削除時の live 配備

dependency を削除する配備では、新 lock の反映前に配備済みの旧 `apm.lock.yaml` を `/tmp/codex/<task>.XXXXXX/` の private な作業記録へ保存する。旧台帳と受入済み lock の差分、撤去対象の実体・hash・所有範囲を照合し、対象と退避先を示して必要な撤去承認を得る。未知・変更済み・読取不能・symlink は保持して報告する。

`chezmoi apply` で新 lock を先に反映すると、後続の `apm install --frozen` と `apm prune` が成功しても旧 skill が残る場合がある。旧 owner の記録が新 lock にないためで、live verifier は残った skill を管理外として報告する。PASS だけで撤去完了としない。

承認済みの撤去には既存 APM の native prune を使う。

1. live source の新 `apm.yml` だけを対象限定で反映し、旧 lock を残す。新 lock まで反映済みの場合は、保存済み旧 lock と受入済み lock の差分が予定した dependency・配備 record の削除だけで、その他の metadata が一致することを確認した上で旧 lock を一時的に戻す。不一致なら戻さず、撤去を保留する。
2. 通常 HOME を cwd にして `apm prune --dry-run` を実行する。dependency・owner・配備先が承認済みの撤去対象だけであることを確認する。dry-run は package 名を表示するが、内部の file は列挙しない。撤去対象として表示された各 `apm_modules` package directory の内容も実行前に確認する。package directory は内容ごと削除されるため、手動追加・変更済み file など保持が必要な内容があれば prune を保留する。全対象の確認と承認がそろってから `apm prune` を実行する。失敗した場合は変更された実体と lock を保存して報告し、再 install や追加削除へ進まない。
3. 撤去対象の通常ファイル・directory・dangling symlink が無いことと、保持対象が変わらないことを確認する。prune が成功しても残存があれば未完了とする。受入済み lock を live source から対象限定で反映する。上書き確認が必要な場合は、[編集・配備ルール](../docs/architecture.md)に従う。
4. `apm install --frozen --target claude,codex --https` を実行し、受入済み lock との一致・下記の live 検証・対象限定の `chezmoi verify` を確認する。旧 lock と実行記録は完了まで保持する。

新 lock の反映から始めた場合の残存と、旧台帳を使う native prune の撤去・変更済み file の保持は、`tests/apm-retirement.bats` が一時 HOME の実 CLI で検証する。通常 HOME の配備や撤去をテストから実行しない。

### live 配備後の APM 確認

live source から対象限定の apply と必要な frozen 同期を終えたら、受入済みlockを基準にHOMEの管理対象を読み取りだけで照合する。`SOURCE_DIR` は検証するhelperのvalidated task worktree、`LIVE_SOURCE` は `chezmoi source-path` が返す受入済みsourceとする。`"$HOME"` は検証入口の起動前に展開し、実際の配備先を渡す。

```bash
python3 "$SOURCE_DIR/scripts/verification_env.py" "$SOURCE_DIR" -- \
  bun "$SOURCE_DIR/scripts/verify-apm-deployment.mjs" --live "$LIVE_SOURCE/apm.lock.yaml" "$HOME"
```

liveモードはroot metadataと所有権ledgerを含むlock全体の一致、管理対象の全file hash、SKILL frontmatter、管理スキル内部の台帳外fileを検査する。APMのLF正規化hashとCRLF実体は既存の共通処理で照合する。lockと管理対象のsymlinkは拒否する。各targetのskill directory直下の管理外entryは、中身やリンク先を読まず一覧で報告し、保持する。配備・削除・lock書換えは行わない。

manifestの一致と対象ファイルの反映は `chezmoi verify`、公開pluginのcurrent stateは既存の両verifierで別に確認する。`apm audit --ci` はlock生成時の隔離runtimeで行う。稼働中のCodexログ等を含むHOME全体へaudit replayを適用せず、liveの完了判断には上記の所有範囲を使う。live比較の成功は隔離auditや管理外スキルの検証を実施したという意味にはしない。

### Impeccable と Design Hook

**Impeccable**: UI の設計・評価・改善を担う user-invoked / model-invoked skill。検証済み commit に pin し、共有ハブ経由で Codex、Claude skill dir 経由で Claude Code へ配布する。Antigravity の可視性は [APM のマルチランタイム配布](#apm-のマルチランタイム配布) の検証状態に従う。新規 UI の create / shape flow は `PRODUCT.md` / `DESIGN.md` の context setup へ誘導し、既存 UI の scoped 改善は context 文書がなくてもブロックしない。直接の前身である `frontend-design` は責務の重複を避けるため撤去した。

**Design Hook**: user-global に **2 イベント**を配線する。per-edit は Claude Code の `Edit|Write|MultiEdit` / Codex の `Edit|Write|apply_patch` に対する `PostToolUse`（timeout 5s）、deep pass はセッション終端の `Stop`（`matcher` なし・timeout 30s。上流 manifest に合わせた値）。Claude は `~/.claude/skills/impeccable/`、Codex は共有ハブ `~/.agents/skills/impeccable/` の `scripts/impeccable hook` を `IMPECCABLE_HOOK_QUIET=1` で呼ぶ。Nix が `IMPECCABLE_BIN` に固定 engine の絶対 path を渡し、管理 command は実行可能な engine と launcher の存在を確認してから呼ぶ。engine がなければ launcher の自動取得へ進まず無言で終了する。runtime 側は stdin の `hook_event_name` でイベントを、`turn_id` で Codex を判別する。Claude Stop は従来の `hookSpecificOutput.additionalContext`、Codex Stop は native の top-level `decision` / `reason` を返し、managed command は両方を fail-open でそのまま通す。

標準 hook の対象ルールは二層で、**両方を配線して初めて両 tier が届く**（[ADR-0029](../docs/adr/0029-impeccable-pin-advance-with-stop-hook.md)）。per-edit は immediate tier を編集箇所へ返し、その他の対象ルールは `Stop` へ先送りする。Stop はセッション中に触れた UI ファイルを再走査して fresh finding をまとめて返す（per-edit が既に出した分は dedupe。何も残っていなければ無言）。4.8.1 / engine 0.1.19 は上流既定の advisory 除外を使い、従来の deferred fixture `overused-font` は対象外となるため、`side-tab` で遅延検出を検証する。`Stop` は `stop_hook_active` を見て再入時は即座に抜ける。

Impeccable 4.1.2 は Stop scan 後に fresh finding だけでなく live finding 全体を cache へ同期する。immediate / deferred の両 tier を持つファイルでも初回 deep pass 後の次回の `Stop` は無言になり、新しい finding が現れるまで再報告しない。4.1.1 までの交互再報告は解消済みで、4.8.1 / engine 0.1.19でもこの動作を維持し、`tests/design-hook.bats` は実際の管理 commandからこの silent convergence を検証する。

finding footerはsession内の初回だけfull policyを出し、以後はshort footerにする。full policyが許容する自己修復の境界はfinding単位の`ignore-value`までで、agentは確信のあるfalse positiveまたはユーザーが許容済みの例外に限って使い、理由をユーザーへ示す。file / rule全体を抑制する`ignore-file` / `ignore-rule`はユーザーの明示承認が必要である。

いずれの層も、clean UI、非 UI、機密・生成物、重複 finding、同一ファイルの編集閾値超過は無言にする。runtime の未配備・内部エラー・非0終了はすべて成功扱いにする advisory feedback であり、編集を拒否する gate ではない。実装中に人間が画面上の対象を選ぶ要素指差しフィードバック、実装後の受入検証 とも役割・主体・タイミングが異なる。Antigravity / Cursor / GitHub Copilot には自動 hook を配線しない。

**UI specialist skill（保持）**: `web-design-guidelines` は Web 実装規則、`modern-web-guidance` は最新 Web API、React 系 skill は React の構成・性能・View Transition、`shadcn` は shadcn/ui、`remotion-best-practices` は動画 UI を担当する。Impeccable はこれらを置き換えず、UI 全体の設計品質を扱う。

**その他 apm skill（保持）**: find-skills, skill-creator, pdf, supabase-postgres-best-practices, empirical-prompt-tuning, effect-ts, security-audit。

**Herdr TUI skill（退役）**: `herdrdev/herdr/skills/herdr` は通常 APM 配備から外した。復旧時に使う旧 revision は `2ecf19a92fc3a7fff75b6ce3655ef04f4625ec01` で、版と copy-env 登録の復旧条件は [ADR-0088](../docs/adr/0088-migrate-herdr-tui-to-app.md#切替と復旧) に記録する。`herdr-peer-refactor` は別の公開 plugin skill で TUI 専用のまま保持し、App 対応済みとして案内しない。

## Ultracite の project hook

`ultracite init` が生成する Claude Code の整形 hook は、各 project の `.claude/settings.json` で `PostToolUse` の `Write|Edit` に対する command を `"\"$HOME/.local/bin/ultracite-fix-hook\""` に置き換える。既存 command と併用せず、他の hook は保持する。

この hook は stdin の `tool_input.file_path` と `$CLAUDE_PROJECT_DIR` の絶対パスを解決し、project 内の通常ファイル1件だけを project の `node_modules/.bin/ultracite fix <file>` へ渡す。実行 cwd は project に固定する。入力不正・対象なし・範囲外（外向き symlink を含む）・競合記号・対象ファイルの repo で merge/rebase 中・Git 状態の検査不能時はスキップする。local CLI がなければ取得せず、整形の失敗は無言で編集を継続する。user-global hook の追加や project 設定の自動書換えは行わない。

## dotfiles 管理の公開 skill plugin

plugin の current-state 検証では、実行時の CLI path / version は記録情報として扱う。CLI の更新だけでは拒否せず、現在の inventory・固定 payload・pin・配備先を照合する。Claude の版更新は、検証済み旧 payload と今回配備した新版 settings の組合せを受け付けるが、未知の source や変更済みの旧 payload は更新前に拒否する。

11件の Agent Skill、5つの共用 CLI、規範契約と WSL2 browser 資産の正本は公開 `treflebonbon/skills` repository にある。dotfiles の唯一の版選択は `~/.config/nix-devshell/skills-plugin.json` で、Claude Code、Codex、Antigravity CLI の公式 plugin 導入と端末固有の config / Nix / dispatch 配線を管理する。第三者 skill は APM から別途導入し、公開 payload を dotfiles に複製したり、独自の dependency resolver を追加したりしない。

`sync-codex-managed-config --verify-only` は current Codex config の exact cache path / grant / deny を照合し、続く `sync-skills-plugin --verify-only` は current pin、固定 checkout、`.git` を除いた source snapshot、receipt、全 runtime の現在の plugin inventory と payload を照合する。成功時の JSON `source` が検証済み source の起点であり、個別資産はそこから `skills/<name>/...`、`contracts/...`、`bin/...` を解決する。receipt に過去の成功が残るだけでは現在の導入や旧配備の撤去を許可しない。いずれかが失敗・未確認なら移行前コピーを保持する。詳細な受入 pin と移行契約は [ADR-0082](../docs/adr/0082-extract-local-skills-to-public-repository.md) を正本とする。

移行対象は `dogfood`、`domain-modeling-studio`、`herdr-peer-refactor`、`marp`、`md-agents-review`、`md-claude-review`、`orca-peer-refactor`、`pr-screenshots`、`rop`、`ui-grill-with-docs`、`worktree-gc`。旧配備から撤去できるのは移行前 revision `6d5b73dd8b9c88531a74e724ca9d83fa34b44b35` の既知の内容に一致する明示対象だけである。unknown、変更済み、読取不能、symlink / special file、検査中に消えた項目や新規追加は、理由と path を残して保持する。対象外の user skill と APM 配備は維持する。旧 source が空または不在でも現行 plugin の導入・同期が成立する。

共用 CLI は `git-push-topic`、`git-push-reviewed`、`gh-review-thread`、`orca-send`、`codex-reviewer`。`sync-skills-plugin --run-cli <name> -- <arguments>` は current public source の CLI を検証して起動し、利用できない場合も固定 legacy snapshot が hash・mode と manifest に一致するときだけその旧 CLI に fallback する。snapshot は `$XDG_STATE_HOME/treflebonbon-skills/legacy/<revision>/`（`XDG_STATE_HOME` 未指定時は `~/.local/state/` 配下）にあり、未知または壊れた snapshot を使わない。raw Codex entry は public source 欠損時に旧 implementation へ fallback しない。

新 pin への更新では `skills-plugin.json` の owner / repo / 完全な rev / tree / version / NAR hash / file count を同じ受入済み source の値に揃える。移行時の `run_onchange_after_codex-managed-sync.sh.tmpl` hook は mutating な `sync-codex-managed-config` の成功後に、`sync-codex-managed-config --verify-only`、`sync-skills-plugin --verify-only`、`legacy_skills retire-known-skills` をこの順で実行する。二つの verifier は現在の Codex cache grant / deny と3 runtime の plugin inventory / payload を読み取り照合し、receipt の過去成功だけでは撤去 gate を通さない。両方成功後に限り、helper が current pin・旧 baseline・5つの live CLI shim と pinned CLI / module / APM lock 所有権を確認し、既知の旧 copy を file 単位で再確認して撤去する。空 directory だけを rmdir する。失敗・不明の path は理由とともに保持する。初回移行では live source から旧 CLI backup の保存だけを先に実行し、その後の `chezmoi diff` で差分を確認する。未知差分があれば保留する。5つの CLI shim を差し替えるときは差分確認後に before hook を実行してから、変更対象 path のみを apply し、その後に after hook を明示実行する。path apply 自体は hook を起動しない。after hook が同期から撤去までを行うため、単独の同期コマンドで代替しない。初回 backup の保存から配備する場合は [Architecture の配備手順](../docs/architecture.md#architecture)を参照する。旧版へ戻す場合は、過去に受け入れた pin record 全体を復元して通常の公式同期と両 read-only 検証を行う。専用 auto の保護設定、有効化、資格情報は自動変更しない。実効状態が未確認ならその起動を保留する。

peer 協働や browser 資産の共通契約は public pin が正本。source path は `sync-skills-plugin --verify-only` の JSON から解決し、`local-skills/` の旧 source copy を参照元にしない（[契約案内](autonomous-peer-contract.md)、[ADR-0075](../docs/adr/0075-adopt-peer-refactor-skills.md)）。

### 解析不能 Bash コマンドの確認（現在は不要）

[ADR-0055](../docs/adr/0055-disable-block-reads-outside-working-directories.md)（2026-09-09）により `permissions.blockReadsOutsideWorkingDirectories` は無効化された。静的解析できない Bash コマンド（heredoc 経由の interpreter、`$(...)` / command substitution、裸の `$VAR`、`sed`/`awk`/`python3 -c` 等）を理由に一律で human confirmation を要求していた仕組み（[2026-09-05 調査ノートの 2026-09-08 追記](../docs/research/claude-code-block-reads-2026-09-05.md#2026-09-08-追記issue-248)、issue #248）はもう働かない。heredoc・command substitution・裸の `$VAR` 展開を確認回避のために避ける必要はない。

ただし `permissions.deny` の `Read(...)` パターン（`~/.ssh/**`・`~/.aws/**` 等の credential 系を含む）は、`Read` tool と `cat`/`head`/`tail`/`grep` 等の認識済み read-only Bash コマンドには `blockReadsOutsideWorkingDirectories` と無関係に引き続き適用される（ADR-0055 で実機検証済み）。`python3 -c`・`node -e`・heredoc 経由の interpreter のようなプログラム経由の読み取りはこの `deny` をすり抜けるため、agent はこれを deny 回避の手段として使わない。`Read`/`Grep`/`Glob` tool が拒否したファイルは、拒否理由を尊重し別の経路で読み直さない。

**Orca native agent launch**: Orca は native worktree を agent の `cwd` にして Agent Picker から built-in agent を起動し、Settings の Agent Permissions で permission mode を所有する。自律 workflow は shipped Yolo、権限確認を残す場合は Manual と Orca Source Control による stage / commit / push を使う。Yolo の worktree isolation は disposable diff の review / recovery 境界であり、filesystem / network を強制する Technical Sandbox Boundary ではない。Orca native Codex の entry / activation に repository wrapper や Active Git Metadata Boundary を挟まない（[ADR-0046](../docs/adr/0046-separate-orca-native-worktree-entry.md)）。

**Codex Runtime Adapter（raw CLI only）**: `codex-worktree` は current linked worktree の physical root、absolute worktree Git dir、absolute Git common dir を inherited `GIT_*` なしで解決し、Codex の公式 `-C` / `-c` interface へ変換する。`.git` pointer → worktree Git dir → `commondir` → common dir と、common dir 直下の `worktrees/<entry>`、worktree Git dir の `gitdir` back-pointer → top-level `.git` を同じ physical ownership chain として検証する。metadata-file-relative target は受理し、不一致は Codex 未起動で fail closed にする。profile は ambient `CODEX_PERMISSION_PROFILE` や managed config の default に委ねず、top-level agent launch が受理する `-c 'default_permissions="dotfiles-secure"'` で固定する（`-P dotfiles-secure` は `codex sandbox` subcommand の直接検証で使う）。primary checkout、non-Git、unresolved metadata、working root / permission boundary を置換・拡張する caller argument、sandbox / hook trust を迂回する dangerous argument は fail closed とし、Git operation や workflow policy を持たない。`codex-orca` は既存 caller 向けに argv をそのまま転送する compatibility entry だが、Orca native session の entry / activation には使わない。managed `dotfiles-secure` config は secret-path deny と network policy を保持するが static repository Git write exception を持たず、Active Git Metadata Boundary は raw adapter が session ごとにだけ追加する（[ADR-0044](../docs/adr/0044-runtime-owned-worktree-entry-and-codex-activation.md)）。

raw adapter は Linux／WSL2 で `devshell-env trust` と worktree ごとの公開入力登録 `devshell-env admit --git-head FULL_SHA -- FILES` を要求する。`codex-worktree`、`devshell-env codex`、`devshell-env admit` は current pin の receipt・checkout・source を検証した後、固定 plugin source の `bin/codex-worktree` と `bin/devshell-env` を実行する。欠損や不一致時は停止し、旧 raw 実装へ fallback しない。登録した Git 履歴・ファイル・公開設定だけをコピーし、Nix／shellHook より前に専用 HOME・store・process・network の境界を作る。起動元の任意変数は復元せず、root dotenv の read 例外も追加しない。管理 permission と Active Git Metadata Boundary は読み取り専用の requirements に固定する。

終了時に commit・index・通常ファイルを元の worktree へ返す。実行中の host 並行編集、未登録入力との衝突、初期化／隔離の失敗では非0終了して結果を保持する。無保護な fallback は使わない。入力登録・導入条件・再起動・復旧は [利用方法](shell-environment.md#raw-codex-のプロジェクト開発環境) を読む。人間の明示 `with-env` は従来の dotenv 注入を保持し、raw の `with-env --prepared` は秘密なしの環境だけを再利用する。管理 Context7・Serena は明示選択して同じ隔離内で起動し、GitHub は人間が確認した公開 repo・topic・CI/外部連携の方針を登録して限定 gateway へ接続する。必要な認証は host に保持する。[対応 CLI と確認条件](shell-environment.md#隔離内の管理-mcp-と-github) を参照する。Orca／Herdr の native 起動、既存セッションには遡及適用しない。

`sync-codex-managed-config` は native Codex home と explicit `CODEX_HOME` の managed `dotfiles-secure` から、旧 absolute `…/.git = "write"` と `:workspace_roots` の `".git" = "write"` を除去する。Codex self-expanded concrete map は、管理設定に明示されていない absolute root と managed workspace の `"."` mode が一致する場合だけ除去する。明示的に管理する `/tmp/codex` の追加拒否ルール、managed profile の独立 nested deny、`:minimal` など他の scalar baseline、user-defined profile の path rule は保持する。

移植元スキルの `eval.yaml` / `tasks/`（skill 評価ハーネス）は持ち込まない。

## playwright-cli

単発のブラウザ操作・スクレイピング・フォーム操作・スクリーンショットは `playwright-cli` skill を優先する。nix devshell のローカル package（`private_dot_config/nix-devshell/packages/playwright-cli.nix`、vendored `@playwright/cli`）を `modules/ai.nix` の shellHook が `~/.agents/skills/playwright-cli` へ symlink 配備する。agent-browser は削除した。PR の画面証拠を収集する場合もこの skill を使う。

WSL2 の通常の `playwright-cli open [URL]` は Windows 側の worktree 別 browser identity を headless で使用する。物理 worktree root から profile・CDP endpoint・Dashboard port・lease を割り当て、同じ worktree の状態を保持する。別 worktree と Dogfood は独立して利用できる。同じ identity の headless / headed 競合は既存 consumer を保持して拒否する。WSL browser へフォールバックしない。

`show` / `show --annotate` は人間の明示開始による headed モードを要求し、その worktree の Dashboard を使う。annotation は lease 所有 session だけに結び付く。背景処理は自動 headed 起動・前面化・OS 入力をしない。終了は session 指定の `close` と対象 Dashboard の `show --kill` を使い、`close-all` / `kill-all` は拒否する。明示 remote CDP attach と WSL browser-free の override 制約は維持する。

profile を初期化する場合は、その worktree で `playwright-cli reset-profile --confirm-identity <identity>` を明示実行する。対象の session・Dashboard・所有権が終了し、Windows 側でも停止を確認できた場合だけ、その worktree profile を削除する。共有添付 profile は対象にできない。

PR 添付は `browser-attachments upload --repo OWNER/REPO --pr NUMBER --image PATH --placeholder TEXT --request-id ID` を使う。旧専用 profile の手動 GitHub 認証を添付専用 identity が引き継ぎ、検証 profile へコピーしない。異なる PR は並列、同じ PR の本文更新は直列にし、更新直前の本文を取得する。asset を保存済みなら同じ request ID で本文更新を再開できる。送信結果不明なら二重送信せず調査する。人間の初回認証・期限切れ対応は `browser-attachments close` の成功を確認 → `browser-attachments auth` → 手動ログイン → `browser-attachments close`。認証不足の添付失敗で残った headless ブラウザも、最初の close で終了してから headed の認証へ進む。添付 CLI の実行は headless のみ。標準の `pr` は本文作成を担当し、この CLI を自動起動しない。

任意の画像補足は `pr-screenshots` を明示的に呼ぶ。`browser-attachments comment --repo OWNER/REPO --pr NUMBER --image PATH [--image PATH] --body-file PATH --request-id ID` が全画像を揃えて1コメントを投稿し、PR 本文は更新しない。原稿には画像順に `<!-- screenshot-1 -->` などを1回ずつ置く。同じ ID は画像・原稿も同じ内容で再利用し、投稿済みコメントのマーカーを照会して重複を防ぐ。途中失敗では画像・取得済み URL・理由を残し、送信結果不明なら状態を調べて再送を避ける。

CLI session の保存先・Dashboard の session 一覧・制御 socket も物理 worktree root ごとに分離する。同じ session 名を別 worktree で使っても相互操作しない。切替前に旧 package で既存 CLI / Dashboard を終了する。Dogfood の自動 CDP port は所有権の予約と同じ lock 内で割り当て、保持中の予約を避ける。明示 port の競合は拒否する。Windows の状態確認が重なる場合、共有の登録 lock は最大30秒待機し、期限超過は状態を保持して失敗する。

### Managed Chrome 所有権の確認と復旧

WSL2 の Playwright と Dogfood は、Nix browser package に同梱する `managed-chrome-owner` を共有する。`MANAGED_CHROME_OWNER` は同梱 CLI の絶対パスを指す。所有権は共通の `BROWSER_OWNERSHIP_DIR`、未指定なら `$XDG_RUNTIME_DIR/browser-ownership`、さらに未設定なら `${TMPDIR:-/tmp}/browser-ownership` に置く。Dogfood 固有のディレクトリ指定がこの場所と異なる場合は拒否する。

`managed-chrome-owner status` で identity ごとの role・所有者・workspace・起動状態を確認する。`locate --role playwright --workspace <physical-root>` の先頭フィールドが対象 identity。終了に失敗した場合は記録された consumer を終了し、`managed-chrome-owner --identity <identity> recover` を実行する。Windows 側の照会が成功し、Chrome が停止済みで、未確定の起動処理もない場合だけ解放する。Chrome の終了要求や profile 削除は行わない。`starting` のまま起動監視 process が異常終了した場合は、後から Chrome を起動し得る処理の完了を証明できないため、記録を保持して調査を要する。

起動コマンドが戻った後の `settled` でも、呼出元が生存して CDP の準備を待っている間は `recover` による回収を拒否する。起動を一度も試みていない `reserved` の予約は、token が一致する caller の通常 `release` で取り消せる。この取消は起動処理と同じ lock 内で token を無効化するため、初期確認で Chrome 未インストールや port/profile 競合を検出した場合も、問題を解消してそのまま再試行できる。

移行は旧版で managed CLI session・Dashboard・Dogfood run を終了してから、Nix package とローカル Dogfood skill を対応する版へ揃え、devShell を再読込みして MANAGED_CHROME_OWNER / DOGFOOD_WINDOWS_SCRIPT 等の同梱ツール参照を更新する。旧 `owner` や `acquire.lock` が残っている場合は起動を拒否するため、切替前に旧版の終了処理と Windows 側の状態を調査する。記録の削除による起動制限の迂回は行わない。設計判断は [ADR-0047](../docs/adr/0047-centralize-managed-chrome-ownership.md) を参照する。

## Claude Code plugin の二層管理

プラグインは「配置（物流）」と「runtime 有効化」を別レイヤーで管理する:

- `apm.yml` — 第三者の外部 plugin / skill の取得（自作の公開 `treflebonbon-skills` は固定版 plugin 同期で管理）
- **`treflebonbon-skills`** — 11件の skill と共用資産を公開固定版から Claude Code / Codex / Antigravity CLI の公式 plugin 経路へ同期する。pin と runtime-specific な設定・dispatch は dotfiles が所有し、payload の source は公開 repository が所有する（上記「dotfiles 管理の公開 skill plugin」、[ADR-0082](../docs/adr/0082-extract-local-skills-to-public-repository.md)）
- `settings.json` `enabledPlugins` — runtime 有効化フラグ。hook を含む plugin（`security-guidance` / LSP 群 / `codex` / `ponytail`）はここで有効化する
- `settings.json` `extraKnownMarketplaces` — 外部 marketplace 宣言（`openai-codex` / `ponytail`、[ADR-0058](../docs/adr/0058-adopt-ponytail-plugin.md)）

`~/.claude/plugins/` 配下の `known_marketplaces.json` / `installed_plugins.json` / `cache/` は Claude Code の runtime state なので git/chezmoi では管理しない。

## Codex plugin marketplace 管理

Codex には Claude Code の `enabledPlugins`/`extraKnownMarketplaces` に相当する、未登録の marketplace を先に宣言するだけで済む仕組みが `config.toml` に無い。marketplace を新規に使えるようにするには `codex plugin marketplace add` を実行して実際に fetch させる必要があり、これは常に命令的な CLI 操作である（一度 fetch 済みの marketplace の情報は `codex` 自身が `[marketplaces.<name>]` として `config.toml` に書き戻すが、書き戻された内容をこちらが事前に書いても `codex` は再 fetch してくれない）。marketplace 登録（`codex plugin marketplace add`）・plugin install（`codex plugin add`）は `private_dot_local/bin/executable_sync-codex-managed-config`（既存の `codex_home` 列挙・`run_onchange` トリガーを持つ）が冪等に行う。`config.toml.tmpl` の `[plugins."<name>@<marketplace>"]` `enabled = true` は、既に登録・install 済みの plugin を有効化するだけの宣言である（[ADR-0058](../docs/adr/0058-adopt-ponytail-plugin.md) 2026-09-11 amendment）。この命令的ステップは `codex` バイナリ不在・対象 `codex_home` の設定不備に対して fail-open にし、`PONYTAIL_MARKETPLACE_SOURCE` を明示的に空にすることで丸ごと無効化できる（`config.toml` への書き戻しが既存の merge/cmp 前提を崩すテストのための逃げ道）。
