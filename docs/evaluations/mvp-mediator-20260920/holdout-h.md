# Holdout H: 保存済み住所とデータ更新

## Deliverable

### 最小アーキテクチャ

| 関心 | 所有者 | 方針 |
| --- | --- | --- |
| 下書き・形式チェック | フォーム | 編集中のフィールド値と形式上のエラーを保持する。保存済み住所の更新では置換しない。 |
| 業務上の検証と保存 | Model／ユースケース | 送信時に業務規則を検証し、住所を保存する。UI やフォームに依存しない。 |
| 送信の UI 状態と単一送信 | 既存の submission binding | 検証済みの送信要求を受け、既存の pending/result と「同時に一件だけ」を用いる。表示専用の reducer、`isSubmitting`、第二の状態機械は加えない。 |
| 実行・寿命・失敗の区別 | Effect の既存実行境界 | ユースケースを実行し、型付きの想定内エラーを結果として binding へ返す。defect と interruption は業務エラーへ潰さず、既存の観測・寿命管理に従う。 |
| 保存済み住所の読取り | 既存の query／購読 | summary と編集画面は独立に購読できる。単一 connector を必須にせず、更新された永続データを各購読へ反映する。 |

送信開始の可否は既存 binding の pending 状態が裁定する。フォームはその可否を再実装せず、送信結果を下書きの値へ自動反映しない。保存済みデータの background refresh は query のデータを更新するだけで、編集中のフォーム下書きと submission state の遷移を起こさない。

このフローには取消も画面間排他もないため、親 Mediator や追加のフロー状態は不要である。既存 binding が送信要求の受理、進行表示、結果表示の接続点になる。

### 振る舞い確認

| 条件 | 期待結果 |
| --- | --- |
| 下書き編集中に background refresh | summary は新しい保存済み住所を表示できる。フォームのフィールド値・形式エラーは変わらず、送信は開始も完了もしない。 |
| 送信中に再度送信 | 既存 binding が二件目を受理せず、一件だけが実行される。 |
| 送信が型付きエラーで失敗 | pending が終了して失敗結果を表示できる。下書きは残り、再送信できる。defect／interruption は同じ業務失敗として表示しない。 |
| 送信が成功 | pending が終了し、保存済み住所の読取りは既存の更新機構で最新値へ収束する。下書きを消す・保存値で置き換える・画面を閉じるかは未指定のため、今回は「下書きを保持する」と仮定する。 |

## 固定要件の達成

| 要件 | 判定 | 理由 |
| --- | --- | --- |
| 1. 業務検証は Model／ユースケース、下書き／形式処理はフォーム | ○ | 所有者を分離し、送信時の業務検証を Model／ユースケースに置いた。 |
| 2. refresh は下書きを上書きせず、自動送信遷移を作らない | ○ | refresh の対象を保存済み読取りだけとし、下書きと submission state を変更しない。 |
| 3. 既存送信状態を使い、第二の同等状態機械を作らず、一件制約を保つ | ○ | 既存 binding を唯一の送信 UI 状態とし、再送信は pending 中に受理しない。 |
| 4. 独立した読取り購読を許し、単一 connector を強制しない | ○ | summary と編集画面の独立購読を明記した。 |
| 5. Effect が実行／寿命／エラーを担い、型付きエラーと defect／interruption を分離 | ○ | Effect の既存実行境界とエラー区別を明記した。 |
| 6. refresh 中編集、送信失敗、成功完了を確認し、成功後の下書き方針を仮定として示す | ○ | 振る舞い確認に三条件を置き、成功後は下書きを保持する仮定を明示した。 |

## Discretionary fill-ins

- 成功後の下書きは保持する、と仮定した。これは利用者が結果を確認しつつ編集を続けられ、background refresh による意図しない上書きも避けられるためである。
- 既存 query が保存成功を反映する契機は、採用済みの無効化・再取得・購読更新のいずれでもよい。新しい同期機構は追加しない。
