# R7-A: 在庫予約ダイアログのアーキテクチャメモ

## Deliverable

### 責務の配置

| 所有者 | 責務 |
| --- | --- |
| 予約ユースケース（Model） | 在庫可否を決め、予約実行時に再検証する。画面が表示用に在庫ルールを複製しない。 |
| `ReservationDialogMediator` | submit、送信中 close/cancel、再送、結果採用を裁定する UI 所有者。現在の試行 ID と取消中かを保持し、同一商品の旧試行の結果を採用しない。 |
| 既存の operation UI binding と Effect 実行境界 | 既存の pending/outcome 状態を公開し、Mediator が受理した試行を実行する。Fiber の中断、Scope による資源解放、終了通知を扱う。型付きの想定内エラー、defect、中断を別種別のまま Mediator へ返す。中断はサーバー側予約のロールバックを意味しない。 |
| 予約ダイアログ View | 数量入力と数値形式チェックを局所に保持し、妥当な入力を submit 要求として Mediator へ送る。close も cancel 要求として送る。 |
| 在庫・予約状況を表示する二つのパネル | 同じ Context から表示状態とイベント送信口を独立して読む。兄弟 View を直接制御せず、Mediator の状態を表示する。 |
| 背景在庫更新 | 既存のデータ取得・再検証経路で在庫表示を更新する。予約試行の遷移や `activeAttemptId` を変更しない。 |

既存 binding の pending/outcome が予約操作そのものを表す限り、それを再利用する。追加するのは全取得状態の複製ではなく、`activeAttemptId`、取消中の試行 ID、結果採用の照合だけである。結果を binding 側で除外できる場合はそれを使い、できない場合も実行境界から試行 ID 付きの終了通知を Mediator に返す。

### イベントと遷移

| 前状態 | イベント | 後状態 | 資源所有者 | 実行効果 |
| --- | --- | --- | --- | --- |
| 編集中 | `submit(validQuantity)` | 送信中 `A` | Effect 実行境界 | Mediator が新しい試行 ID `A` を発行して binding に実行を要求する。ユースケースが在庫を実行時に再検証する。 |
| 送信中 `A` | 背景在庫更新 | 送信中 `A` | 変更なし | 表示用在庫だけを更新し、予約の pending/outcome と試行 ID は維持する。 |
| 送信中 `A` | `close` | 取消中 `A` | Effect 実行境界 | Mediator が取消を受理し、実行境界へ Fiber 中断と必要な解放を要求する。サーバー側の取消済みとは表示しない。 |
| 取消中 `A` | 中断・解放完了通知 | 閉じた状態（再度開けば編集中） | 実行境界から解放 | `A` の実行寿命を終え、次の submit を許可する。 |
| 閉じた状態 | 開く | 編集中 | なし | 再度の入力を受け付ける。 |
| 編集中（`A` を取消後） | `submit(validQuantity)` | 送信中 `B` | Effect 実行境界 | 新しい試行 ID `B` を発行する。同じ商品の試行でも `A` と区別する。 |
| 送信中 `B` | `A` の成功／想定内失敗／defect／遅延終了通知 | 送信中 `B` | 実行境界が `A` を解放 | Mediator は `A` の表示結果を不採用にし、必要な解放完了だけを処理する。 |
| 送信中 `B` | `B` の成功 | 成功 `B` | binding の outcome | Mediator が `B` と照合して成功を表示へ採用する。 |
| 送信中 `B` | `B` の想定内失敗 | 失敗 `B` | binding の outcome | Mediator が `B` と照合して業務エラーを表示へ採用する。 |
| 送信中 `B` | `B` の defect または中断 | 技術失敗 `B` または取消遷移 | 実行境界 | defect は想定内業務エラーに変換せず、中断は Mediator の取消方針に従って扱う。 |

`A` の成功と失敗のどちらも `B` の表示を上書きできない。結果除外を reducer の比較だけで済ませず、実行境界／binding が試行 ID を保った通知と資源解放を行えることを接続契約に含める。

### 確認項目

| シナリオ | 期待結果 |
| --- | --- |
| 表示在庫後に他者が在庫を消費して予約する | View は独自の在庫判定をせず、ユースケースが実行時に拒否し、その想定内エラーを表示する。 |
| `A` の送信中に close する | Mediator が `A` の取消を裁定し、実行境界が中断・解放を行う。中断表示からサーバー側のロールバックを推論しない。 |
| `A` を取消後に同じ商品を `B` として送信し、`A` の成功が遅延到着する | `B` は送信中のままで、`A` の成功は採用されない。`A` の解放通知だけが処理される。 |
| 同じ手順で `A` の想定内失敗が遅延到着する | `B` の pending／outcome を上書きせず、`A` の失敗は表示されない。 |
| `B` の結果が届く | `B` の ID と一致する結果だけを採用し、成功、想定内失敗、defect、中断を区別する。 |
| `A` または `B` の送信中に背景在庫更新が届く | 二つのパネルの在庫表示は更新できるが、ダイアログの送信状態、取消状態、試行 ID、結果採用は変化しない。 |
| 二つの Context 利用 View を同時に表示する | どちらも同じ Mediator の送信口を使え、入力の数量・形式チェックはダイアログだけに残る。転送専用コンポーネントは不要である。 |

## 自己報告

### 六つの達成判定

| 項目 | 判定 | 根拠 |
| --- | --- | --- |
| 1. 在庫方針の所有と実行時再検証 | ○ | Model／ユースケースへ所有を置き、表示側の第二在庫ルールを明示的に置かなかった。 |
| 2. submit/cancel/結果採用の UI 所有者と旧試行の除外 | ○ | `ReservationDialogMediator` を命名し、`A` と `B` の ID 照合で旧成功・旧失敗を不採用とした。 |
| 3. Effect の実行・中断・寿命とエラーの区別 | ○ | 実行境界へ委譲し、想定内エラー、defect、中断、サーバーロールバックを同一視しなかった。 |
| 4. Context 複数購読と局所入力処理 | ○ | 二つのパネルの独立購読と、ダイアログ内の数量・形式チェックを維持し、転送層を要求しなかった。 |
| 5. 既存 operation state の再利用と追加状態の限定 | ○ | pending/outcome は binding を再利用し、取消・試行照合だけを Mediator の追加調整状態とした。 |
| 6. 背景更新中の送信を含む具体的な遷移確認 | ○ | 状態遷移表と確認項目に、送信中の背景更新、取消、再送、旧結果到着を含めた。 |

### 曖昧点

| Issue | Cause | General Fix Rule |
| --- | --- | --- |
| 既存 operation binding が試行 ID 付きの結果・中断完了通知を公開できるかは未指定。 | シナリオは pending/outcome の公開だけを述べ、同一商品の旧試行との相関方法を定めていない。 | binding と Mediator の境界で操作 ID を維持し、旧結果の表示採用を除外しつつ、資源解放に必要な終了通知は必ず処理する。ID 比較を UI reducer だけに閉じ込めない。 |

### 任意補完

- 新しい submit は、取消した試行の中断・解放完了が確認できてから受理する前提とした。これにより既存 binding の一操作 pending 制約を破らない。
- 結果を採用しない旧試行についても、実行境界はその終了と資源解放を通知する前提とした。
- package version、Effect API、アプリケーションコードは選定・記述していない。
