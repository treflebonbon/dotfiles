# MVP評価チェッカーの設計

状態: 設計確定。Q1・Q2はユーザーが「推奨」、Q3は「確定」と回答。実装はv10契約・checkerとして進行中。最終検証結果は[MVP評価専用の実行入口](../../mvp-evaluation-runner.md)に記録する。

## 起点となる事実

[v9評価](../mvp-mediator-evaluation-v9/run-20260922-01/results.md)の01 Eでは、許容されたopaque stateのnull-prototype tokenとstructuredCloneの結果が、遷移を呼ぶ前から一致しない。固定checkerの0/52を52件の機能不良とは判定していない。

同じ成果物の自己検査は、WeakMap内の論理状態を含まずにtokenを比較していた。チェッカーの誤判定と、実行者の純粋性検査不足は別の問題。現在のobserveの4値と、将来の判断にも使う全保持状態は同義ではない。

旧runの本文・成果物・採点・証拠は保存し、次の評価へ結果を転用しない。

## 合意した設計判断

Q1（合意済み）: 評価基盤に限定する。ユーザー回答「Q1:推奨」。

- 推奨: チェッカー、必要な評価用API契約、版固定・検査を対象とし、v9スキル本文は保持する。変更の原因を分離できる。
- 代案: スキルの検証指示も同時に整える。整合は取りやすいが、次回結果の変化をどちらへ帰属できるかが弱まる。

Q2（合意済み）: 全判断状態を明示的なデータに限定する。ユーザー回答「Q2:推奨」。

- 推奨: この評価用モデルの全判断状態を、通常object・配列・単純値からなる明示的なデータへ置く契約に限定する。内部のフィールド名・構成は自由で、機能期待値はobserve/effectsを使う。コピー可能な全状態のsnapshotと同入力の結果を比較し、別のinspect APIは追加しない。実アプリの状態表現を制限するものではない。旧opaque自由契約からの変更なので、旧版との単純な改善率比較はできない。
- 代案A: opaque内部表現を維持し、全判断状態を返す検査用inspect APIを必須にする。表現自由度は保てるが、追加APIとその内容の完全性を監査する必要がある。
- 代案B: observe/effectsと後続操作の振る舞いだけを検査する。API追加は不要だが、未公開状態の非破壊性は保証できず、純粋性確認の範囲が狭まる。

調査済み: 現行checkerはstate自体のstructuredClone前後比較を使う（check-device.mjs:15–28）。observeはphase/owner/desired/operationIdのみで、採番nextや失敗段階など全判断状態を含まない。表示投影だけの比較への変更では現在の純粋性条件を満たす証拠にならない。検査用APIでも有限の検査でも、任意のプログラム全体の純粋性を数学的に証明するわけではない。

## Q3 — 設計全体（合意済み）

### 目的・対象・非目標

E課題の固定チェッカーについて、許容する状態表現と比較前提を一致させ、入力非破壊性・同入力の決定性を検査可能にする。スキル本文はv9のまま保持する。今回新たに制限するのはE課題の抽象モデルAPIであり、S/B/Lの課題、実アプリの表現、6機能基準・critical指定は変更しない。スキルの行分け改善、汎用検証フレームワーク、実行runtime変更は対象外。

### 状態表現

全判断状態をstate内に含め、通常のobject（Object.prototype）・配列・null・boolean・string・有限numberからなる循環のないデータとする。フィールド名・内部構成は自由。objectのフィールドは列挙可能な文字列キーのデータプロパティ、配列は欠落要素や追加プロパティのない通常配列とする。freezeは許容する。

WeakMapやクロージャ等へ判断用の可変状態を隠す表現は契約外。関数、getter/setter、symbol、独自class/prototype、null-prototype、Map/Set、undefined等を状態へ含めない。これは一般アプリへの規則ではなく、今回選んだ評価用データ契約の具体化である。

許容形式は初期状態と各遷移の返却状態で検査し、不適合箇所を示す。外部に隠された判断状態の有無は親のコード監査でも確認する。有限のテストで任意のプログラムの純粋性を証明したとは主張しない。

### 検査と失敗の扱い

各検査対象遷移では、初回呼出し前に入力stateをsnapshotし、初回と再呼出しのそれぞれの直後に入力が変わっていないことを照合する。同じ入力state/eventで得た全返却stateとeffectsを比較して決定性を確認する。初回返却値も再呼出し前にsnapshotし、2回目が同じ参照を書き換えても検出できるようにする。effectsは実行せず、従来の機能検査の履歴へ採用するのは初回結果だけとする。

機能期待値は引き続きobserve/effectsで検査し、特定の内部フィールド名を要求しない。従来の52機能ケースと既知の誤動作を検出するnegative controlを維持する。

状態形式不適合は「モデルの契約違反」、前後不一致や同入力不一致は対応するモデル検査の失敗、チェッカー自身の実行不能は「検査未成立」と区別する。いずれも非0終了にし、実際に実行・完了したケースと未実行を分ける。検査前の失敗を52件の機能失敗へ展開しない。モデルの契約違反を配布入力のinvalidへ付け替えてreplacementすることもしない。6項目とC1〜C4は既存の根拠別採点を維持し、新たな一律減点は追加しない。

### 実装・版管理

旧protocol/checker/runを変更せず、新版のE契約・checkerを別ファイルとして固定する。既存CLIの新版E配布元・checker hash照合と対応fixtureを更新し、旧版のstatus参照・証拠保存を維持する。古い停止済みrunを新版で再開・再採点しない。配布プロンプトのE節以外の共通テンプレートは維持する。

同じスキルでも課題APIと検査が変わるので、次の実LLM runは新しい評価条件として扱い、旧版との単純な改善率比較をしない。E/B/S各3組、直列監査、再発停止、上限、L条件、canonical metadataの扱いは維持する。実LLM評価は実装完了後の明示的なempirical-prompt-tuning依頼で開始する。

### 受入検査

- 通常のデータ状態とfreeze済み状態は、52機能検査と非破壊・決定性検査に合格する。
- 公開observe値が同じでもstate内の採番値等を破壊するモデル、および同入力で結果が変わるモデルを検出する。
- 同じ返却objectの再利用・後続書換えでも、初回返却値のsnapshotによって決定性の不一致を検出する。
- 許容外の状態は具体的な契約違反として検出し、cloneのprototype差をmutationと誤報しない。準備失敗時に52機能失敗と記録しない。
- 新版Eだけが配布され、正しいchecker hashが要求されることを公開CLI fixtureで確認する。旧記録・v9本文の不変も確認する。

実装はtddの回帰検査、型確認、必要な既存テスト、Standards/Specレビューを経る。実LLMの行動改善はこれらのfixture成功からは主張しない。
