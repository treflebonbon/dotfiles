# S2: 最新検索試行だけを採用する責務

## 責務マップ

| 担当 | 責務 |
| --- | --- |
| 既存の search binding / Query 実行層 | 検索の実行、通常の `pending` と `result` の保持、取消要求の伝達。 |
| `SearchMediator` | この画面における唯一の結果採用所有者。検索ごとに `requestId` を発行し、最新 ID と一致する成功・失敗だけを binding へ渡す。 |
| View | binding の `pending` / `result` を表示し、入力を `search(text)` として通知する。 |
| ヘルプ tooltip | View 内だけで開閉する局所表示。検索要求、取消、結果採用には関与しない。 |

同じ文字列を再入力しても別の要求であるため、text の等値ではなく試行ごとの `requestId` を使う。既存 binding が実行と通常の `pending` / `result` を持ち続け、追加するのは Mediator の受信時照合だけである。新しい検索時の Query 取消は実行層へ依頼できるが最善努力であり、サーバーで処理済みの作業を巻き戻したとは扱わない。したがって、取消の成否に依存せず遅延した成功・失敗も ID で除外する。Effect、Atom、独自 scheduler、Promise 制御は導入しない。

| 前状態 | イベント | 後状態 | 資源所有者 | 実行効果 |
| --- | --- | --- | --- | --- |
| 任意 | `search(text)` | 最新 request が pending | binding | binding が検索を開始。前試行があれば取消を依頼する。 |
| 最新 request が pending | 古い request の success / failure | 最新 request が pending のまま | binding | 結果を採用しない。 |
| 最新 request が pending | 最新 request の success | success result | binding | binding が結果を公開する。 |
| 最新 request が pending | 最新 request の failure | failure result | binding | binding が失敗を公開する。 |

## 実行した確認と限界

`node docs/evaluations/mvp-mediator-executable/s2.mjs` を実行し、`s2 self-check: passed` を確認した。自己検査は同一 text の連続入力で ID が異なること、古い success と failure が新しい pending/result を変えないこと、最新 success と最新 failure が適用されること、取消が要求として記録されることを assertion で確認する。

これは純粋モデルの検査であり、React、TanStack Query、ブラウザ、ネットワーク、実際の取消伝播との統合を確認したものではない。実装では既存 binding の完了通知を `SearchMediator.receive(requestId, outcome)` と同じ ID 照合点へ接続する必要がある。

## 凍結済み基準

| 基準 | 判定 | 理由 |
| --- | --- | --- |
| 1. 最新要求 ID | ○ | 同一 text でも `requestId` は増加し、受信は ID 一致だけで採用する。 |
| 2. stale と current の実行検査 | ○ | stale success/failure 後も新要求は pending のまま、current success/failure は assertion で適用を確認した。 |
| 3. 既存 binding の再利用 | ○ | 実行と `pending` / `result` は binding が所有し、Mediator は採用可否だけを追加する。 |
| 4. Effect 等を強制しない | ○ | Effect/Atom、独自 scheduler、Promise の巻戻しは使わず、取消は実行層への要求としてだけ表す。 |
| 5. tooltip と採用所有者 | ○ | tooltip は View の局所状態、`SearchMediator` は一意に命名した結果採用所有者である。 |
| 6. 一致・実行・限界 | ○ | 本メモと `s2.mjs` は同じ ID 照合方針で、自己検査の実行結果と統合未検証の限界を記載した。 |

## 不明点、原因、一般修正規則

不明点は、実際の既存 binding が完了通知に request ID を公開できるかである。原因は、text や Query の取消状態だけでは同一 text の別試行と遅延完了を区別できないことにある。一般修正規則は、重なる UI 操作では開始時に操作 ID を発行し、表示へ反映する成功・失敗の直前に、その ID を現在の操作 ID と一箇所で照合することである。

## 裁量と再試行

裁量として、binding を既存 Query binding の純粋な最小模型にし、現実の通信や React 接続は加えなかった。取消は optional な実行層への要求だけを記録して、結果採用の正しさを取消へ依存させなかった。自己検査の再試行回数は 0 回である。
