# E1 実行モデルメモ

## 成果物の責務と実施済み検証

`e1.mjs` は親 Mediator の純粋な判断だけを表す。`start` の排他方針、最新 intent、停止・解放の順序、失敗後の明示的再試行、古い完了の破棄を所有し、Effect 実行境界には `acquire`、`stop`、`release` コマンドだけを返す。実行境界は I/O、typed error／defect／中断／lifetime を所有する。recording と calibration の子フローの局所 UI、および profile editor はこのモデルの外部で独立し、`profile` は状態も effect も変えない。

実際に `node docs/evaluations/mvp-mediator-executable/e1.mjs` を実行し、`e1 self-check: passed` を確認した。assertion は、取得中に recording → calibration → recording と intent が戻る場合の取得 ID 維持、停止失敗の block、block 中 start の intent 更新だけ、stop/release の段階別再試行と新 ID、release 後の最新 target 取得、古い完了の無視、profile の独立性を検証した。加えて Node の `assert` で入力 state が変化しないことと、active の同 owner start が同一 state と空 effects を返すことを確認し、`API immutability/no-op check: passed` を得た。提案のみの確認はない。

## 六基準

| 基準 | 判定 | 理由 |
| --- | --- | --- |
| 1 | ○ | acquiring、stopping、releasing、blocked の全待機 phase で start は desired を更新する。acquiring で元 target へ戻った場合は既存 acquire ID を維持し I/O を出さない。 |
| 2 | ○ | stop 成功後だけ release、release 成功後だけ acquire を出す。各失敗は blocked にし、retry は失敗した stop または release だけを新 ID で再実行する。 |
| 3 | ○ | stage 開始と retry ごとに単調増加 ID を採番する。現在の operationId と一致しない ok/fail は同一 state と空 effects を返す。 |
| 4 | ○ | モデルは command を返すだけの純粋関数で、scheduler、I/O、Effect runtime を実装しない。親の排他方針と実行境界の責務を分離した。 |
| 5 | ○ | profile は no-op として明示し、子フローの局所 UI 状態をモデルへ持ち込まない。 |
| 6 | ○ | この表の各遷移は同梱 assertion で再生し、実行結果を上記へ記録した。 |

## Unclear Issue / Cause / General Fix Rule

- Issue: acquire 失敗後に desired を消すか保持するかは明記されていない。
- Cause: 「idle に戻る」と「最新 intent」の表示上の意味が分かれている。
- General Fix Rule: 明示的 start でのみ acquire を再開するため、desired は最後の利用者 intent として保持し、retry は idle では無効にする。これにより自動再試行を避け、観測可能な intent を失わない。

## 裁量と再試行

- ID は run 内で `device-1` から単調増加させる文字列とした。各 `initial()` は別 run の新規状態である。
- blocked 中に intent が旧 owner へ戻っても、既に開始済みの stop/release は取り消さず、解放後に最新 target を acquire する。停止・解放成功を次の acquire の前提にする方針を優先した。
- retry は blocked の `failedStage` が `stop` または `release` のときだけ effect を一つ出す。acquire failure は idle へ戻り自動 retry しない。
- canonical usage metrics は利用できないため、数値を作成・記録していない。
