# S: held-out search UI

## 責務マップ

| 所有者 | 責務 |
| --- | --- |
| Search Model / API | 検索を実行し、入力の業務上の検証とサーバー応答を扱う。React と Query の表示判断は持たない。 |
| 既存 Query binding（実行層） | `run` の `{ requestId, text }` を使って検索を起動し、各要求の通常の pending/result/error 通知を発行する。取消は既存の best-effort 機能へ委ね、サーバー処理の巻戻しとは扱わない。 |
| Search result Mediator | 最新の要求 ID、表示への成功・失敗採用、pending の遷移を一箇所で裁定する。同じ文字列でも要求ごとに新しい ID を割り当てる。 |
| Passive View | `search`、binding からの `success` / `failure` を Mediator へ通知し、Mediator の `view` を表示する。ヘルプ tooltip の開閉だけを局所状態として持つ。 |

追加する協調状態は `latestRequestId` だけである。検索実行、通常の Query pending/result/error、取消機構は既存 binding を使う。tooltip は検索要求・ID・結果採用に参加しない。結果採用の UI 所有者は **Search result Mediator** である。

## 状態・イベント

| 前状態 | イベント | 後状態 | 実行効果 |
| --- | --- | --- | --- |
| 任意 | `search(text)` | 新 ID を latest にし、`pending: true`、結果と error を空にする | binding に `{ requestId, text }` を渡す |
| latest の pending | `success(id, result)`（`id === latestRequestId`） | `pending: false`、result を採用 | なし |
| latest の pending | `failure(id, error)`（`id === latestRequestId`） | `pending: false`、error を採用 | なし |
| 任意 | `success` / `failure`（古い ID） | 変化なし | なし |

ID は文字列ではなく要求単位で比較する。したがって `dogs` を再入力した 3 回目の要求は、同じ `dogs` の 2 回目の失敗を採用しない。新要求の時点で以前の表示を空にする方針をこの最小モデルは選んだ。前回結果を保持する UI でも、同じ ID 判定を既存 binding の表示選択箇所に適用できる。

## 実際の検証と限界

`node docs/evaluations/mvp-mediator-executable/s3.mjs` を実行し、成功した。自己検査は以下を `node:assert/strict` で確認する。

1. request 1 の成功を表示した後、request 2 を開始すると pending の表示になる。
2. request 1 の遅延成功と遅延失敗は、request 2 の pending/result を変更しない。
3. request 2 の成功は表示へ採用される。
4. 同じ文字列 `dogs` の request 3 を開始した後、request 2 の失敗は捨て、request 3 の失敗は採用される。

これは純粋な協調モデルのイベント列だけを検証する。React、Query binding、ブラウザー、通信取消、実サーバーがこの ID を通知・伝播する統合動作は実行していない。取消は best effort であり、このモデルもサーバー停止を主張しない。

## 凍結基準

| 基準 | 判定 | 根拠 |
| --- | --- | --- |
| 1 | ○ | `latestRequestId` と要求ごとの連番で成功・失敗を照合し、同文再入力も ID 3 として区別する。 |
| 2 | ○ | 実行済み self-check が古い成功・失敗の無変更と、最新成功・失敗の採用を assert する。 |
| 3 | ○ | 実行と通常通知は既存 Query binding に残し、追加状態を結果採用の ID に限定した。 |
| 4 | ○ | Effect、Atom、自作 scheduler/promise を導入せず、取消をサーバー巻戻しの根拠にしない。 |
| 5 | ○ | tooltip は View の局所状態であり、結果採用の所有者を Search result Mediator と明記した。 |
| 6 | ○ | memo と `s3.mjs` は同じ ID 採用規則で、自己検査を実行済みとし、統合未検証の限界を明記した。 |

## 不明点と一般規則

- Unclear Issue: 既存 binding が request ID を成功・失敗通知にどのように保持・返却するかは与えられていない。
- Cause: 同じ検索文字列では再試行を識別できず、遅延応答の採否を決められない。
- General Fix Rule: 起動時に生成した要求 ID を binding の完了通知まで保持し、表示を変える成功・失敗は Mediator で最新 ID と一致する場合だけ採用する。

## 裁量と再試行

- 裁量: 新検索時に前回 result/error を空にする表示方針を選んだ。前回結果保持の UI は ID 規則を変えずに実装できる。
- 再試行回数: 0 回。最初の自己検査が成功した。
