## 凍結基準

| 基準 | 判定 | 根拠 |
| --- | --- | --- |
| 1 | ○ | acquisition / stopping / releasing / blocked の `start` は desired のみを最新化し、進行中 ID と effect を増やさない。取得成功後は最新 desired と照合する。 |
| 2 | ○ | stop 成功後だけ release を発行し、release 成功後だけ acquire を発行する。失敗は `blocked` にし、`retry` は失敗した stage のみを新 ID で反復する。 |
| 3 | ○ | `nextId` で stage ごと・retry ごとに新 ID を発行し、現在 `operationId` と一致しない completion は不変にする。 |
| 4 | ○ | モデルは共通親の純粋な裁定であり、Effect の実行・エラー分類・中断・寿命管理は外部 command consumer に残す。 |
| 5 | ○ | `profile` は不変結果を返す。device の状態に profile 固有状態を加えていない。 |
| 6 | ○ | 上記 self-check は実装どおりの遷移を assertion で実行し、この表では実行済みと未実行を分離した。 |

## 不明点と一般修正規則

不明点: 実行境界が acquire 成功後の stop / release にどの Effect API を使うかは、この抽象モデルからは決められない。

原因: 実行層の API と寿命管理は入力仕様に含まれない。

一般修正規則: effect consumer は `id` を保持して completion を同じ `id` で親 Mediator に戻し、実行の中断・解放は Effect の既存の Fiber / Scope 方針に委ねる。

裁量: ID は 1 始まりの単調増加整数、blocked 中の `operationId` は null とした。作業上のやり直しは 0 回。self-check では明示 `retry` event を 2 回再生した。
