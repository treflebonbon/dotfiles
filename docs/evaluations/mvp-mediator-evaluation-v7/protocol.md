## 維持する条件と比較の制限

v7では状態表の記入順序だけを理由にC3 failや `state-table-after-model` と判定しない。全保持状態の用途・所有者・区分・本実装の取得元、未確認時の確認対象は引き続き評価する。順序要件の緩和で違反が消えても改善実績には数えない。版をまたぐ比較では状態説明・検証報告の正確さを個別に示し、C3やclear数の変化だけから性能改善を主張しない。

旧契約・runの入力・成果物・採点は変更せず、v6を再採点しない。新規runはv2〜v7契約と新本文のhash・実行入口を固定する。旧runのstatus参照は維持し、新版による書込み再開は認めない。

## 実装Contract

1. 状態表で全保持状態を説明する要件を維持し、事前整理は推奨、記入順序は完了条件外と明記する。最終照合に事前作成の必須条件を残さない。
2. 実行検査の観測時点・期待値・assertion・実行結果の説明を根拠表へ集約する。要件別の達成欄は実装箇所と表の対応ケースを参照し、コードを読んだ確認と実行検査を区別する。
3. 必須検査の不足は追加・再実行で埋める。未検証事項と提案のみの未実行、通常経路の分離、純粋性、導出表示、既存の責務分担・適用範囲を維持する。
4. 改善範囲はskill単体。公開CLIのinit/prepareで新本文とv2〜v7契約を固定・配布する版登録だけを更新し、runtime・採点ロジック・配布テンプレートを変更しない。
5. 前節の比較制限を次回評価へ引き継ぎ、要件変更による違反の減少と成果物の品質改善を分ける。

検証境界は合意済み公開CLI fixture。専用Batsで新版固定・配布のred→green、型確認、全体テスト、Standards/Specレビューを行う。fixtureは行動改善の証明には使わない。
