# 送信中表示 と help tooltip の整理案（最小変更案）

## 1. 前提（既存の所有者の確認）

- 既存の Atom binding（`@effect/atom-react`）が pending／result／error（AsyncResult 相当）と操作識別を所有する。二重送信抑止と古い結果の除外はこの binding が既に保証し、テスト済みという前提を採用し、本メモではこの機構自体を再検証しない。
- フォームは入力値と形式チェックを所有する。業務検証はユースケース（Model）が実行時に行う。
- 複数の Context consumer は、既存 Context 経由でこの binding の状態を読む。
- 今回、新しい排他・取消方針は導入しない。送信中表示フローと help tooltip は競合しないため、両者を裁定する共通の親（Mediator／CoR）は不要。

## 2. 操作方針（最小変更案）

- **送信中表示**: 各 Context consumer は既存 binding の pending／result／error をそのまま読み、その場で表示に変換する。まとめ役の `selectDisplay` や新しい共有 hook・Provider は追加しない。複数 consumer が同じ値を読むという要件は、既存 Context がすでに満たしている。新設の裁定（採用ID等）はない＝「導出表示」規約の対象外。
- **二重送信抑止・古い結果の除外**: 既存 binding の保証をそのまま使う。新しい `isSubmitting` フラグや操作 ID を追加しない。
- **help tooltip**: 業務フロー・送信状態と無関係な、独立した View ローカル状態（例: `useState<boolean>`）として扱う。tooltip の開閉はどの Context consumer の表示にも、送信可否にも影響しない。Context には置かない。
- **実装上の注意点（新しい業務制約ではない）**: tooltip のトリガー要素が `<form>` 内にある場合は `type="button"` を明示し、クリックによる意図しない submit を防ぐ。

**今回の実際の表示変更点**: 表示分岐は waiting を先に判定し、再送信中は「送信中」表示を出し、前回のエラー（および前回の成功表示）はその間非表示にする（Case B／B2／H）。この分岐ルールは全 Context consumer で同一にする＝各 consumer が個別に `isSubmitting` や前回結果のコピーを持たない。

## 3. 状態の説明

説明対象の保持状態は `tooltipOpen` のみ。送信中表示に使う pending／result／error・操作識別・入力値・形式チェックは既存機構がすでに所有しており、本提案では追加保持しない。

| 状態 | 判断に使う目的・所有者 | 本実装での情報源 |
| --- | --- | --- |
| `tooltipOpen` | help tooltip の開閉表示。所有者は当該 tooltip を表示する View 自身 | 当該 View の局所 state（`useState` 等）。Context には置かず、他の consumer に公開しない |

## 4. 具体的な確認ケースと期待値

| # | 操作列 | 期待値 |
| --- | --- | --- |
| A: 通常送信 | 未送信 → 送信 → 完了（成功） | 送信中は binding の pending を反映して「送信中」表示、完了後は result を反映して成功表示 |
| B: 失敗後の再送信（コアケース） | 送信 → 失敗（前回の失敗が result／error に載る） → 再送信 → 完了（成功／失敗） | 再送信中は「送信中」表示になり、前回の失敗と現在の送信中を区別する。採用方針: **再送信中は前回のエラーメッセージを非表示にし、送信中である旨のみを表示する**（前回結果を別枠で残す方針を取る場合は本メモを更新する） |
| B2: 成功後の再送信 | 送信 → 成功 → 再送信 → 完了 | 再送信中は「送信中」表示のみで、前回の成功表示は非表示にする |
| C: tooltip 開閉が送信状態に影響しない | 送信中に tooltip を開く → 閉じる | pending／result／error は不変。送信ボタンの disabled 状態も不変 |
| D: tooltip トリガーが送信を誘発しない | tooltip トリガーをクリックして開閉 | 新しい送信要求が発行されない。binding は非送信中のまま維持される（トリガーが `<form>` 内なら `type="button"` であることが前提） |
| E: tooltip 開閉が他 consumer に波及しない | tooltip を開く → 他の Context consumer（送信ボタン・エラー表示等）の表示を確認 | 他 consumer が読む値（pending／result／error）は変化しない。tooltip の開閉状態はどの Context にも公開されない |
| F: フォーム形式エラー時の送信ボタン | フォーム形式エラーがある状態で送信ボタン押下 | 業務検証（ユースケース）に到達せず、送信要求自体が発行されない（disabled で押下できないか、押下しても停止するかは既存フォームの挙動に従う）。いずれの場合も disabled の判定条件に業務規則を含めない |
| G: 業務検証エラー時の表示 | フォーム形式は正しいが業務検証（ユースケース）が拒否 | binding の result／error（型付きエラー）を表示し、フォームの形式エラー表示とは別枠で扱う。UI 側で業務規則を再判定しない |
| H: 複数 consumer の表示一致（コアケース） | 送信 → 失敗 → 再送信、送信ボタンとエラー表示欄の 2 つの Context consumer で同時観測 | 再送信中は両 consumer とも「送信中」を表示し、前回のエラーを両方とも非表示にする。分岐ルールは全 consumer で同一で、各 consumer が独自の送信中フラグ・前回結果コピーを持たない。いずれかの consumer が送信要求を送れる場合は、既存 binding の送信口をそのまま呼ぶ（consumer 固有のハンドラを持たない） |
| I: tooltip の開閉状態が送信結果の描画で失われない | tooltip を開く → 送信 → 送信中 → 完了（成功／失敗） | tooltip はこの間ずっと開いたまま維持され、再マウントされない（表示分岐の実装が tooltip を含むサブツリーごと差し替える構成だと、この期待値が崩れる） |

## 6. 確認する境界・除外した境界

選んだ境界:
- **状態の再利用**: 送信中表示は既存 binding からそのまま導出し、追加保持しない（§3、Case A/B/B2/H）。
- **局所表示の独立性**: tooltip は他の表示・送信可否に影響しない、他 consumer にも波及しない（Case C/D/E/I）。
- **業務の実行時検証**: disabled や表示の判断が業務規則を UI 側で再実装していない（Case F/G）。

除外した境界:
- **必要な終了・解放**: 今回新しい排他・取消方針を導入しないため対象外（フローが競合しない）。
- **同じ対象への再試行と古い応答の除外機構自体**: タスク前提として「既に保証・テスト済み」とされているため、本メモでは機構自体を再検証しない。ただし、その保証の上でどう表示を区別するか（Case B/B2）は確認対象に含めた。

## 7. 未確認・未実行の範囲

- 導入版の `AsyncResult`（または相当型）で「再送信中（waiting）」がどう表現されるかは未確認。具体的には、waiting が Success／Failure と共存できるフィールド（例: 各 variant が持つ `waiting: boolean`）なのか、Initial／Success／Failure と排他な別 tag なのかを確認する必要がある。表示分岐が結果の tag（Initial／Success／Failure）だけで分けており waiting フィールドを見落としていると、Case B／B2／H の「前回結果と送信中の区別」が誤表示になり得る。→ 導入版の型定義（`node_modules/effect` 配下の Atom／AsyncResult 実装）を確認する。
- 実アプリでの実機確認は行っていない（実行モデル・API コードを作成していないため）。
- node による自動チェックは作成・実行していない（本タスクは提案のみで、実アプリ・実行モデル・API コードが不要とされているため）。
