# 送信中表示 / help tooltip 整理メモ

## 前提（今回スコープ外・再検証しない）

- 既存 binding が `pending` / `result` / `error` と操作識別を保有し、二重送信抑止・古い結果（stale result）の除外はすでに保証されテスト済み。→ **表示層でこれらを再実装・再ガードしない。**
- フォームは入力値と形式チェック（必須・型・桁数など）を所有。業務検証（ユースケース側のエラー）とは別物。
- 複数の Context consumer が表示を読む。
- 新しい排他・取消方針（キャンセル、AbortController、入力ロック等）は今回対象外。

## 最小変更案

1. **送信中表示は binding の `pending` をそのまま使う。**
   派生 state・新しい atom・新しい Context を作らない。「submitting かどうか」の判定式を各 consumer がそれぞれ書くと表示がズレる原因になるので、判定は 1 箇所（既存 binding の値、または既存の selector）に寄せ、全 consumer が同じ値を読む形に揃える。
   また、`pending ? <Spinner/> : <Form/>` のようにフォーム自体を丸ごと出し替えない。フォームをアンマウントすると tooltip のローカル開閉 state、フォーカス、未確定の入力値が失われる。送信中表示はインライン表示かオーバーレイとして重ね、フォームの subtree は維持する。

2. **`result` / `error` のローカルコピーを作らない。**
   表示用に `useState`/`useEffect` で `result`/`error` をミラーしない。ミラーすると binding が既に解決した stale result 問題を表示層で再発させる。常に binding の現在値をそのまま描画する。

3. **形式エラーと業務エラーの表示領域を分ける。**
   - 形式エラー：フォームのローカル state から、ユースケース呼び出し無しに即時表示（フィールド直下）。
   - 業務エラー：binding の `error`/`result` から、フォームレベルの別領域に表示。
   - 両者を同じ「エラー枠」に統合しない（原因が混ざって見えるため）。

4. **help tooltip は表示・状態ともに完全独立にする。**
   - 開閉状態はコンポーネントローカル（`useState` 等）で持ち、送信用 Context/binding を購読しない。`pending` の変化で tooltip が閉じたり状態がリセットされたりしないようにする。
   - help トリガーは送信ボタンの中・上に重ねない。送信中にボタンが disabled になると、disabled 要素は hover/focus イベントを受け取れず tooltip が動作しなくなるため、トリガーはボタン外に独立して置く。
   - `<form>` 内に置く場合、トリガーは `type="button"` にする（未指定だとクリックでフォーム送信が走る）。

5. **新しい排他・取消ロジックは足さない。**
   送信中にボタンを視覚的に disabled 表示すること自体は良いが、それは「表示」であって二重送信抑止のガードではない（ガードは既存 binding 側にすでにある）。キャンセルボタンや AbortController、入力ロックは追加しない。

6. **アクセシビリティは最低限入れる（省略しない）。**
   - 送信中表示：`role="status"` の領域を **1 つだけ** 常時マウントしておき、テキストだけを出し替える（`aria-live="polite"` は `role="status"` に含意されるので併記不要）。複数 Context consumer がそれぞれ `role="status"` を出すと、スクリーンリーダーが同じ内容を重複して読み上げるため、実際に読み上げる領域は 1 箇所に絞り、他の consumer は視覚表示のみにする。`aria-busy` は読み上げそのものは行わないので、必要なら補助的に併用する程度に留める。
   - tooltip：トリガーに `aria-describedby`、tooltip 本体に `role="tooltip"`。hover だけでなく focus でも開き、`Esc` で閉じる。

> 注：`@effect/atom-react` 側の具体的な API 名（`Result` のバリアント名、フック名など）はこのメモでは断定しない。実装時に既存 binding のコードを確認して当てはめること（要確認）。

## 具体的な確認項目（表示層のみ。二重送信抑止・stale result 除外そのものは対象外）

- [ ] `pending` が true になった瞬間、全ての Context consumer が同時に送信中表示に切り替わる（一部の consumer だけ古い表示のまま残らない）。
- [ ] `pending` が false に戻った瞬間、全ての consumer が同時に送信中表示を解除する。
- [ ] 読み上げ用の `role="status"` 領域が画面全体で 1 つだけであり、常時マウントされたままテキストのみ更新されている（`pending` が true になったタイミングで新規マウントされていない）。
- [ ] 送信中表示の切り替えでフォームの subtree がアンマウントされていない（同じ input 要素・フォーカス位置・未確定の入力値が送信前後で保持される）。
- [ ] tooltip を開いた状態で送信を実行しても、`pending` の変化で tooltip が閉じたり位置がずれたりしない。
- [ ] help トリガーをクリックしてもフォームが送信されない。
- [ ] 送信中でも help トリガーはキーボードフォーカスで開ける（disabled なボタンに重なっていないか）。
- [ ] `Esc` で tooltip が閉じる。
- [ ] 形式エラー（未入力・桁数超過等）はユースケースを呼ばずに即時表示される。
- [ ] 業務エラー（ユースケース起因）はフィールドの形式エラー枠ではなく、フォームレベルの領域に表示される。
- [ ] 再送信して binding 側が `result`/`error` を更新したら、表示も追随して更新される（表示側に古い値を握ったままの `useState`/`useEffect` が無いことをコードで確認）。
- [ ] 新規追加コードに、送信の中断・キャンセル・入力ロックに関するロジックが増えていない（grep で確認）。

## スコープ外（今回変更しない）

- 二重送信抑止ロジック本体
- 古い結果（stale result）の除外ロジック本体
- 新しい排他・取消方針の導入
- 実アプリコード・実行モデル・API 実装
