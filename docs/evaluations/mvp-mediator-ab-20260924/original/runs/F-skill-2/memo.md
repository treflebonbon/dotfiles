# フォーム送信中表示 / help tooltip 整理メモ（最小変更案）

## 前提（既存の所有者）

- 業務検証はユースケースが実行時に持つ。フォームは入力値と形式チェックのみを所有する。
- 送受信状態（pending / result / error）と操作識別は既存 binding（`@effect/atom-react` の Atom）が所有する。
- 二重送信抑止・古い結果（stale result）の除外は既存 binding が既に保証し、テスト済み。
- 複数の Context consumer が表示を読む。
- 今回、フロー間の新しい排他・取消方針は導入しない。

以上より、今回の作業は「既存の保証を再実装しない」「送信中表示と tooltip の開閉を混在させない」という整理（tidy）であり、新しい Mediator・状態機械・操作 ID を追加する変更ではない。

## 操作方針

1. **送信中表示は既存 binding からの導出のみにする**
   - 各 Context consumer は、同じ Atom の `pending / result / error` を読む共通の導出関数（例: `selectSubmitDisplay(bindingState)`）を経由して表示を作る。
   - 個々の View が独自の `isSubmitting` ローカル状態や、別の操作 ID を持たない。複数 consumer が同じ判断を同じ所有者（既存 binding）から受け取ることを揃える。
   - 二重送信抑止・古い結果除外は既存 binding の責務のまま。今回の変更でこれらを再実装・再検証しない。
   - 前回結果（error）を保持したまま再送信で処理中に戻る binding では、導出関数側で「前回の失敗表示」と「今回の送信中表示」を区別する規則を 1 つ決める（前回 error を隠す、または進行中と並記する、のいずれか）。区別のためだけの新しい状態（`lastError` や `isRetrying` 等）は追加しない。
2. **help tooltip は送信フローから独立させる**
   - tooltip の開閉は表示条件の分岐であり、View のローカル状態（例: `useState` の真偽値）として保持する。
   - tooltip の開閉イベントは送信可否・進行中状態・キャンセルのいずれにも作用させない（他 View への裁定を経由しない）。
   - 「閉じると送信を取り消す」性質を持たせない（本タスクの前提どおり独立表示のみ）。
   - 独立性は双方向で保つ：tooltip の開閉が送信状態に作用しないことに加え、送信の開始・完了・失敗によって `tooltipOpen` がリセットされない（条件分岐や再マウントで tooltip 表示部分を巻き込まない）ことも満たす。
3. **業務検証・入力形式チェックには手を入れない**
   - フォームの入力値・形式チェック、ユースケース側の業務検証は既存のまま。表示整理のために抽象モデルや状態機械を新設しない。

## 状態の説明（追加・保持する状態）

| 状態 | 判断に使う目的・所有者 | 本実装での情報源 |
| --- | --- | --- |
| `pending` / `result` / `error`（既存） | 送信中表示・二重送信抑止・古い結果除外の判断。既存 binding（Atom）が所有。今回は追加しない。 | 既存の `@effect/atom-react` binding。複数 Context consumer は同じ Atom を購読し、共通の導出関数経由で表示化する。 |
| `tooltipOpen` | help tooltip の開閉表示のみ。当該 View が所有し、他 View・送信フローに影響しない。 | 各 View のローカル状態（例: `useState`）。Context 越しに共有しない。 |

説明対象の保持状態は上記 2 行のみ。新規の操作 ID・排他状態・取消方針は追加しない。
