# 送信中表示 / helpツールチップ 整理メモ

## 前提（今回は変更しない・再検証しない領域）

- pending / result / error、および「どの操作の結果か」の識別は既存bindingが所有する。二重送信抑止・古い結果の除外はそのbinding側で既に保証済み・テスト済みという前提を採用し、表示側で再実装・再検証しない。
- 入力値の保持と形式チェック（必須・型・パターン等の同期チェック）はフォームが所有する。
- 業務検証（ドメインルールに基づくエラー）はユースケース側にあり、bindingが返すresultのエラー種別として表示側に届く。
- pending/result/errorは複数のContext consumerが読む構成が既にある。
- 新しい排他制御・キャンセル方針は作らない（bindingの既存保証をなぞるだけ）。

この前提から外れる変更（binding内部のロジック変更、requestId/世代管理の作り直し、新しいAbort/キャンセルの導入）はスコープ外とする。

## 最小変更方針

やることは2つだけ。

1. **送信中表示**: 既存Contextが公開しているpending/result/errorをそのまま参照して見た目を出す。新しい状態は持たない。
2. **helpツールチップ**: 送信状態と無関係な情報なので、送信用Contextには一切繋がない独立したローカルUI状態として実装する。

判断軸は「既にある状態を再利用できるか」「新しい状態を持つ必要が本当にあるか」の2点で、どちらも既存資産の再利用で足りる。

### 送信中表示

- 既存Contextから`pending`（またはbindingが返す`Result`の待機フラグ）をそのまま`useContext`/`useAtomValue`的な既存の参照経路で読むだけにする。表示コンポーネント側にpendingのローカルコピーやtimerベースの疑似pendingを作らない。
- 表示の出し分けは3値（pending中 / 成功 / 失敗）で足り、失敗表示は「形式エラー（フォーム）」と「業務エラー（ユースケース由来、resultのエラー）」を別チャネル・別文言で出す。両者を1つのエラー文字列に混ぜない。
- 複数のContext consumerがある場合、各consumerは同じContextの値をそのまま描画するだけにし、consumerごとにpendingを別変数へコピーして独自にrender判定しない（コピーするとconsumer間で表示がズレる回帰を作り込みやすい）。
- ボタンのdisabled等、二重送信抑止に見える挙動があっても、それは既存binding側の保証の結果として出るのであって、表示コンポーネント側でuseState等による独自の「送信済みフラグ」は追加しない。

### helpツールチップ

- 送信中表示とは無関係なので、送信用Contextの中に混ぜ込まない。ツールチップの開閉はコンポーネントローカルな`useState`（またはネイティブの`<details>`/`popover`属性）で十分。新しいContextやatomを追加する必要はない（遠く離れた複数コンポーネントで開閉状態を共有する要求が今回ない以上、共有state化はYAGNI）。
- pending/result/errorの変化（送信開始・成功・失敗）を理由にツールチップを強制的に開閉するコードを書かない。逆に、ツールチップの開閉が送信処理のトリガーやpending状態に影響しないことを保証する（イベントハンドラを完全に分離する）。

## 具体的な確認項目

送信中表示:

1. pendingがtrueの間、送信中の見た目（例: 送信ボタン無効化＋「送信中」テキストやスピナー）が出る。判定に使っている値が既存bindingのpendingそのものであり、表示側で新規に持ったフラグでないことをdiffで確認する。
2. 送信成功（Success）でpendingがfalseに戻ったとき、画面上の全Context consumerが同時に非pending表示へ切り替わる（consumer間で表示タイミングがズレない）。
3. 送信失敗（Failure）時、ユースケース由来の業務エラーとフォームの形式チェックエラーが別々の表示箇所・文言で出て、混在しない。
4. 古い（先行して送信して後から返ってきた）操作の結果が画面に反映されない（binding側の除外保証を表示側が壊していないかを1ケースだけ回帰確認する。表示側で除外ロジックを新規実装していないことも合わせて確認）。
5. 連続クリック等をしても二重送信されない（binding側の既存保証の再確認のみで、表示側に新規の抑止コードが増えていないことをdiffで確認する）。

helpツールチップ（独立性の確認）:

6. 送信中（pending中）でもツールチップの開閉操作ができる。
7. ツールチップの開閉が、pending/result/errorのいずれの値・表示にも影響しない（開閉前後でContextの値が変化しない）。
8. 送信成功・失敗による再描画で、開いていたツールチップが意図せず閉じられない（送信状態からの副作用でツールチップのstateが変更されるコードが無いことをdiffで確認）。
9. ツールチップのstateがコンポーネントローカルであり、送信用Contextやグローバルstateに漏れていない（複数のフォームインスタンスがある場合、片方の開閉がもう片方に影響しない）。

横断・スコープ確認:

10. 今回の変更で新しい排他制御・キャンセル（AbortController、世代カウンタ等）のロジックが追加されていない（diffレビューで、binding内部や操作識別まわりのファイルに変更が無いことを確認）。
11. アクセシビリティ: 送信中表示のライブリージョン（aria-live等）とツールチップのaria-expanded/aria-describedbyが独立しており、フォーカス管理・スクリーンリーダー読み上げが競合しない。

## スコープ外（今回やらない）

- binding内部のpending/result/error算出ロジック、操作識別（世代・requestId等）の変更・再テスト。
- 二重送信抑止・古い結果除外の新規実装（既存保証を前提として利用するのみ）。
- 業務検証ロジックのユースケースからの移動・変更。
- helpツールチップと送信状態を共有する新しいContext/atomの新設。
