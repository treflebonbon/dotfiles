# rop-visualizer の解析補助比較

2026-09-11。`grill-with-docs` で確定した計画を、同じ task worktree で実装・実行した。

## 検証する問い

開発可能な TypeScript／Rust プロジェクトで、構文・型・参照先の根拠を機械抽出すると、AI が作る ROP フロー図の経路が正確になるか。

「経路の正確さ」はソースに反する経路・説明がないこと。「正しく説明できる範囲」は固定した意味要件を図と説明が満たす範囲。不明点を増やして誤断定を隠す方式は採用しない。

## 確定した実験

- TypeScript：現行、ast-grep、ts-morph。Rust：現行、ast-grep、syn、syn＋rust-analyzer。
- 既存3ケース、型・参照解決用の複数ファイル2ケース、公開実装2ケース。各条件3反復、生成75回。
- 公開実装は Effect の `retryTransient` と ripgrep の `main`／`run`。commit、取得物のハッシュ、ライセンスは [公開入力 manifest](rop-public-inputs.json) に記録する。
- 解析器は根拠を返し、AI が既存形式の `flow.json` を作る。生成前にソースだけから正解を決める。方式名を伏せた別コンテキストのレビューを行う。
- 本導入・スキル配布・live source の apply は今回の範囲に含めない。

手順・採否基準・実行プログラムは [実験ディレクトリ](../../tests/experiments/rop-analysis/README.md) を参照する。成果物は `tmp/rop-analysis-comparison/`。過去のスキル評価と凍結 fixture は変更しない。

## 候補の根拠

[ast-grep](https://ast-grep.github.io/advanced/faq.html#does-ast-grep-support-some-advanced-static-analysis) は構文検索に使えるが、型・スコープ・制御フロー解析は提供しない。[ts-morph](https://ts-morph.com/navigation/type-checker) は TypeScript の型チェッカーと解決済みシグネチャにアクセスできる。[syn](https://docs.rs/syn/2.0.119/syn/) は Rust の構文木を扱い、[rust-analyzer](https://rust-analyzer.github.io/book/contributing/architecture.html) は名前解決・型推論を提供する。今回の RA 条件は syn の構文抽出を共通にし、LSP の hover・definition を追加する。

[quote](https://docs.rs/quote/latest/quote/) はトークン生成、[prettyplease](https://docs.rs/prettyplease/latest/prettyplease/) は構文木の整形出力が目的なので、解析精度の比較条件には加えない。実コード抜粋には元ソースの行を使う。

## 結果

**次の導入候補は TypeScript が ast-grep、Rust は現行維持。** 元の盲検集計と、後述の評価器の誤判定6件を除く追加分析で、推奨は一致した。補正後は ts-morph も採用基準を満たすが、ast-grep と誤断定・要件充足が同点のため、事前に決めた組み込み負担の順位で ast-grep を選ぶ。

ただし、TypeScript の差は現行の生成形式エラー1件と、Effect の構築時／実行時についての非重大な説明誤り1件が中心である。型解析が構文解析より経路を正確にするという結果は得られなかった。Rust は補正後に全方式の誤断定が0件で、「現行より減る」という採用条件を満たせない。今回の結果だけで本導入は行わない。

具体的な差と同点の内容：

- TypeScript 現行の `run-049` は不正な JSON 制御文字で生成失敗。手直し・再生成せず、充足0として集計した。`run-074` は `validate(input)` の条件評価が checkout 呼び出し時に行われるのに「実行時は入力を検証」と書いた。経路の接続自体は正しく、重大違反ではない。
- 同名の `Label.catchTag`／`Label::or_else`、Array.map、import alias、クロージャ内の `?`、回復後の監査などは、形式エラーを除く全方式で要件を満たした。このコーパスでは、型情報の追加による差は出なかった。
- 公開 TypeScript の要件差は、options-first／self-first の両呼出形式の明記。Rust checkout の差は、実際には最終エラー変換へ到達しない `InventoryUnavailable → Unavailable` の定義まで明記したかによる。これらを経路の重大な欠陥と解釈しない。
- syn＋RA の2出力は、`index()` が `usize` と分かったため `> 0` の不成立を `== 0` と表した。型を知らない評価器がこれを誤りとしたので、追加分析では誤断定を除き、対応する固定要件の充足を戻した。これは型情報が正当な説明を可能にした例だが、基準方式に存在した誤りを減らした例ではない。

## 実行環境と再現性

生成は Codex CLI 0.154.0、`gpt-6-astra`、reasoning effort `medium`。各回を fresh context で実行し、外部ツールの使用を禁止した。75回すべてのネイティブイベントを確認し、ツール呼び出しはなかった。同一ケース・方式の3反復はプロンプトのハッシュが一致する。解析証拠の追加以外は入力ソースと指示を揃えた。

入力・正解要件・抽出器・依存 lock・プロンプトなど73ファイルを生成前に凍結し、生成後も SHA-256 が一致した。既存3 fixture のソースは元ファイルとバイト単位で一致する。公開入力は Effect `2465abd571eafa548654f8865711b30798d0867f` と ripgrep `3fce3b5bb0236da2df6d99672afb8a719642eca7`。前者は Effect 3.9.2、後者は `unstable-index` feature を有効にした Linux の構成で解析した。

抽出器は ts-morph 28.0.0、ast-grep 0.45.1、syn 2.0.119、rust-analyzer 2026-08-03。Rust のビルド検証は rustc/cargo 1.97.1。TypeScript 全3ケースは型診断0件、Rust 全4ケースは `cargo check` に成功した。Rust の Unicode を含むソース範囲も抽出器の実行結果で確認した。

生成75回のネイティブ使用量は input 2,004,249 tokens、output 235,087 tokens。レビュー7回は input 397,282 tokens、output 70,312 tokens。この値は請求額の推定ではない。

## 表示と検査コード

7ケースから機械検査に成功した最初の匿名 run を1件ずつ選び、既存 renderer で HTML を生成した。1440px と390pxで、テキスト重なり、無関係なノードを横切る辺、接続位置、body overflow、JavaScript エラーを検査し、キーボード選択・ソース表示・経路選択・リセットを確認した。外部通信を遮断した状態で動作する。採否判定後には ast-grep の TypeScript 3ケースをすべてカバーするよう追加2件（run-029／run-019）も同じ検査に通した。

リトライ例は同じ辺を複数回通る named path を持つ。表示側は各 SVG 辺を一度だけ強調するため正常だが、既存ブラウザ検査が重複を含む期待値と比較して失敗した。`rop-browser-check.py` の期待値を集合に直し、失敗時の記録を保持して再検証した。renderer contract にも、反復経路を保持しつつグラフの辺は重複生成しないテストを追加した。実験単体テスト7件、renderer contract 8件が成功した。配布される renderer と skill は変更していない。

ripgrep の代表図は分岐が多く、1440pxでもグラフ領域の横スクロールを要する。狭い画面では他の図もグラフ領域をスクロールする。意味の採点と表示の検査は別であり、表示検査の成功だけでは意味の正しさを保証しない。

## 解釈の限界

比較対象は今回実装した証拠抽出器と固定プロンプトの組み合わせであり、各ライブラリが到達できる最高精度ではない。型・参照情報を渡しても、AI がその情報を経路へ正しく反映する保証はない。完全な CFG、マクロ展開、実行時情報を抽出した実験でもない。

公開実装は選んだ関数・行範囲だけを生成側へ渡し、呼び先の内部は境界とした。プロジェクト全体を自律探索する能力は測っていない。正解要件は生成前に固定したが、採点は人間の独立した複数評価者ではなく、ケースごとの別コンテキストによる AI レビューである。方式名を伏せても、出力の文体や残った証拠への言及から条件を完全に秘匿できるとは限らない。

各条件3反復の記述的比較であり、統計的優位性や読者の理解時間の改善は示さない。また、正解要件は省略を測る指標でもあるため、到達しないエラー変換の明記など、図の読者にとっての有用性とは別の細かさを評価する場合がある。

## 盲検採点の監査と追加分析

盲検レビューは抽出証拠を受け取らない。そのため、生成結果が補助型情報を引用した4件を、証拠の出所が存在しないと誤判定した。`run-041`、`run-050`、`run-068` は `Fx.Effect<string, Failed, never>`、`run-031` は callback の request が `Effect.Effect<ClientRequest.HttpClientRequest, any, any>` という情報である。いずれも保存済みの生成プロンプトに該当情報が存在した。後者だけは重大違反として採点されていたが、この判定根拠も同じ問題を持つ。

元のレビューと `summary.json` は変更せず、[追加分析スクリプト](../../tests/experiments/rop-analysis/sensitivity.py) が証拠文字列・元の指摘件数・重大度を検証して、この4指摘と、`usize` の型情報を見落とした `run-008`／`run-036` の2指摘を除いた `sensitivity.json` を作る。このスクリプトはレビュー後に追加したもので、生成前の凍結73ファイルには含まれない。正解要件、生成失敗、採用基準は変えない。後者2件だけは同じ誤判定に由来する `search-dispatch-and-propagation` の未充足も充足へ戻す。これは事前登録された一次集計を置き換えるものではなく、評価器の既知の誤判定に対する感度分析である。

## PRレビューの追加修正

公開入力の準備時に、取得アーカイブと、展開後または既存の展開先のソース・package manifest・licenseを記録済みSHA-256と照合するようにした。既存の展開先を無条件に信頼せず、不一致やルートの曖昧さがあれば、元ファイルを上書きせず停止する。保存済みのEffectとripgrepについて、これらのハッシュが一致することも確認した。

テスト側でrepo内の一時ディレクトリの親を作成するようにし、`tmp/` が存在しないcheckout相当の環境でも18テストすべてが成功した。新しい回帰テストは、不正なアーカイブ、選択ファイルの不一致・欠落、既存展開先の変更、複数ルート、package/licenseの不一致を検証する。生成・採点・観測値の変更はなく、実験時の原記録は保持している。
