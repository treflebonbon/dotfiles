# ユーザー環境キャッシュの鮮度と更新失敗の扱いを共通化する

従来のユーザー環境キャッシュの更新判定は `.nix` と `flake.lock` の更新時刻だけを参照し、package に含まれる `.mjs` などの変更を見逃していた。また、従来は Nix が途中出力を残して失敗した場合、呼出し元の `pipefail` 設定次第で旧キャッシュを上書きしていた。候補01「環境キャッシュ」の設計対話で、以下の方針・module の責務・検証範囲を2026-09-07に確定した。

## 実装状況

- [#223](https://github.com/treflebonbon/dotfiles/issues/223) で実装済み: Nix の非0終了、空・bash 構文不正の出力、一時ファイル準備・置換の失敗では旧キャッシュを保持する。通常の配備・APM 配備・初回導入は既存の必須更新指定で停止し、対話シェルは背景更新の完了を待たず起動する。既存の読込み interface と shell option の扱いを維持する。
- [#224](https://github.com/treflebonbon/dotfiles/issues/224) で実装済み: 入力内容と選択環境による鮮度判定、旧形式からの移行、キャッシュと対応入力情報の一体化。ファイル・ディレクトリの相対名、内容、実行可能性、symlink のリンク先、WSL／通常環境の選択を SHA-256 で比較する。入力情報は bash コメントとしてキャッシュに含め、検査済みの生成結果と一度の rename で採用する。比較情報の形式は内部実装であり、新しい公開 interface にしない。
- [#225](https://github.com/treflebonbon/dotfiles/issues/225) で実装済み: OS のファイルロックによる更新の排他、待機後の入力再確認、評価前後の入力照合と最大1回の再試行、更新プロセス終了後の復旧。背景更新は競合時に待たず省略し、必須更新は待機する。二度目の評価でも入力が変われば旧キャッシュを保持し、必須更新は失敗する。親の全14ACとの対応・最終形の実 Nix・未確認環境は [#225 検証記録](../research/user-environment-cache-225-verification.md) に残す。

比較対象は配備された devShell 配下のソース一式。ルートの `.git`／`.direnv` と、Nix の出力リンク `result`／`result-*` を除外する（`result*` は symlink の場合のみ）。拡張子・mtime に依存せず、空ディレクトリや隠しファイルも比較する。キャッシュと更新ログは既存どおりソース外の `~/.cache` に置く。

指紋計算は初期 PATH の `sha256sum`、なければ `shasum -a 256` を使い、生成した devShell の Python／Node 等には依存しない。どちらも利用できない、またはソースを読めない場合は必須更新を失敗させる。確認済み環境・実 Nix の観測・未確認範囲は [#224 検証記録](../research/user-environment-cache-224-verification.md) を参照。

排他には system Perl の `flock` を使い、native `flock(2)` を持つ Linux／WSL／macOS を対象とする。生成する devShell 自体の Perl や、macOS に標準搭載されない `flock` CLI には依存しない。`install.sh` は `git`／`curl`／`perl` の欠損、Perl の native flock 非対応、`sha256sum` と `shasum` 両方の欠損を配備前に検出する。native flock のない Perl は emulation に委ねず失敗させる。これらの依存は初回生成に限らず、以後のキャッシュ更新でも必要になる。

ロック用ファイルは `<cache>.lock` に固定し、削除・置換しない。更新関数の呼出しに限定して開く記述子を Perl に渡し、終了・返却時の kernel による解放を使う。Nix の評価子と入力確認を待つ中間の Bash process には記述子を残さない。これにより更新元が終了しても残存する評価子によってロックを保持し続けない。生成物は一意な一時ファイルへ書かれ、更新元を失った子 process は採用処理へ進めない。正常終了・失敗時には一時出力を除き、強制終了で残った `<cache>.tmp.*`／`<cache>.err.*` は次回のロック取得後に回収する。呼出し元の signal trap は置換しない。

## 鮮度保証の境界

2026-09-08、[PR #236 のレビュー](https://github.com/treflebonbon/dotfiles/pull/236#pullrequestreview-5134154836) を受け、ユーザーは評価前後の入力照合で検出した変化を扱う範囲を選択した。ロックが直列化するのは同じキャッシュへの更新処理であり、ソースを編集・配備する書込み側は参加しない。入力の読取り全体や、入力照合とキャッシュ置換をまとめた原子的なスナップショットは保証しない。

最後の入力照合が終わってからキャッシュの rename までにソースが変わった場合は、変更前の入力に対応するキャッシュを採用し、必須更新も成功することがある。そのキャッシュに記録される入力情報も変更前のものであり、次回の更新で現在の入力との不一致を検出して再生成する。配備成功は、任意の並行書込みに対する採用時点の最新性を保証する意味ではない。

単一ファイルの採用と失敗・中断時の旧キャッシュ保護を維持する。採用後の検査と巻戻しは、検査中に候補が読み手へ見えることや、中断時の復旧処理を増やすため追加しない。採用時点まで入力不変を厳密に保証するには、ソースの書込み側も含めた排他など、別の契約が必要になる。

## Decision

- 対話シェルの起動は旧キャッシュを即座に利用し、背景で更新する。更新失敗でシェル起動を止めず、旧キャッシュを保持する。
- `chezmoi apply` と初回導入は、必須更新で照合した入力に対応するキャッシュを要求する。鮮度保証は上記の境界に従う。更新が必要な場合に生成が失敗したら、その実行を失敗として停止し、成功扱いで後続処理へ進めない。停止までに完了した配備の巻き戻しを意味しない。
- 変更検知は、配備されたユーザー devShell の対象ソース一式について、拡張子によらず内容・追加・削除と、WSL／通常環境の選択を含める。更新時刻を保持した差し替えも検知する。
- `refresh_nix_devshell_cache`／`ensure_nix_devshell_env` の既存 interface を維持する。更新 module が入力照合・排他・評価・結果検査・採用を所有し、読み込み adapter は既存の役割を保つ。背景／必須の用途指定には既存の `NIX_DEVSHELL_CACHE_REQUIRED` を使い、通常の配備・初回導入にも必須更新を適用する。
- 生成の成否と旧キャッシュの保護を呼出し元の shell option に依存させない。失敗した Nix の途中出力をキャッシュとして採用しない。
- 同じキャッシュへの更新は同時に1つだけ実行する。背景更新は既存の更新と重なれば省略し、配備・初回導入は先行更新の終了を待って現在の入力との一致を再確認する。
- 評価前後の入力照合で変化を検出した結果は採用せず、最新の入力で1回だけ自動再試行する。再び変化を検出した場合は旧キャッシュを保持し、配備・初回導入は失敗、背景更新は次の更新機会へ委ねる。
- 生成元を確認できない旧形式のキャッシュは、シェルでは従来どおり利用できるが、必須更新では現在の入力に対応するものへ再生成する。
- キャッシュと対応する入力情報は整合した単位で置換する。生成・採用の失敗や更新プロセスの終了で旧キャッシュを壊さず、次の更新を妨げる状態を残さない。
- bash／zsh の読み込み adapter は維持する。bash は既存の次プロンプトでの再読込、zsh は次のシェル起動での取込みを維持し、両シェルの反映時期の統一やプロジェクト固有の direnv 環境との再合成は今回の対象に含めない。

## Trade-offs

すべての起動で最新の入力との一致を待つと、Nix の評価やダウンロードが日常のシェル起動を止める。一方、配備でも旧キャッシュによる続行を許すと、ソースを更新しても古いツールを使う状態を成功と見なしてしまう。起動時の可用性と配備時の鮮度を区別し、生成失敗時にはどちらも旧キャッシュを保護する。

内容の確認には更新時刻だけの比較より処理が必要だが、拡張子一覧の保守、削除の見逃し、更新時刻を保持した差し替えによる更新漏れを避けることを優先する。

配備は先行更新の待機と入力変化時の再評価で時間が延び得る。背景更新は重複を省き、自動再試行は1回に限ることで、ターミナル起動ごとの待機処理の蓄積と、編集が続く間の無制限な再評価を避ける。

既存 interface のまま更新判断を module 内へ集めることで depth を増やす。各呼出し側には同じ保証を得る leverage、保守側には判断と検証が一か所に集まる locality をもたらす。

## 検証方針

呼出し側とテストは同じ interface を通す。一時 filesystem と Nix の test adapter を module 内部の seam に置き、次の観測可能な結果を検証する。

- 対象ソースの内容・追加・削除・更新時刻を保持した差し替え・環境選択の変更で更新され、変更がなければ再評価しない。旧形式は再生成へ移行する。
- 途中出力を伴う Nix の失敗、結果検査・置換の失敗、更新プロセスの終了で旧キャッシュが保護され、その後の更新を実行できる。`pipefail` の有無で採用結果を変えない。
- 背景更新と必須更新の競合で古い結果が後から上書きされず、必須更新は待機後に入力を再確認する。生成中に入力が変わった場合の再試行は1回に限る。
- 通常の配備・APM 配備・初回導入は必須更新の失敗で停止する。script の文字列・順序の検査だけで済ませず、入口から実行して後続処理が走らないことを確認する。
- bash／zsh の既存の読み込み、シェル識別情報の保持、キャッシュ不在時の起動継続を維持する。これらの振る舞いを検証する既存テストを残し、旧更新方式に依存する検査は同じ interface から更新後の振る舞いを検証するものへ置き換える。

実 Nix での生成・読込み確認は一時領域で行い、task worktree から live source や HOME の配備を更新しない。実行済みの結果と確認範囲は #224／#225 の検証記録を参照する。
