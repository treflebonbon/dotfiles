# React / TanStack / Effect への当てはめ

このスタックを採用済みのプロジェクト向けの実装例。[SKILL.md](../SKILL.md) の責務分担を具体化する。TanStack Query など既存の選択を尊重し、Atom への移行を前提にしない。

Effect の実装前に、導入版の `node_modules/effect/AGENTS.md` があれば全文と必要な参照先を読む。API・import path・Atom の並行実行や購読の挙動は導入版のソースと公式ドキュメントで確認する。以下は特定バージョンの API を固定しない構成例である。

## Root と UI 接続

TanStack Router の Root Route は全体の組立箇所にできる。Effect の依存関係は既存の Service／Layer 構成で供給し、Atom を採用している場合は Registry の配置と寿命を必要な共有範囲に合わせる。ルートをまたいで保持する状態と、フロー終了時に解放するリソースを区別する。

View は props または Context から表示状態とイベント送信口を受け取る。複数の購読箇所や compound components を許す。購読が取得を起動する仕組みなら、その起動と寿命も設計済みの方針に含める。イベント送信は共有した裁定処理へ接続し、View ごとに業務規則や排他判断を置かない。

## 例1: 注文一覧からのキャンセル

| 箇所 | 実装する内容 |
| --- | --- |
| Model／ユースケース | 注文キャンセルの規則と実行時の検証。Effect は成功値・型付きエラー・必要な依存関係を表す。React や Atom を使わずに呼べるようにする。 |
| 注文フローの Mediator | 取消要求を受け、進行中の UI 操作との関係を裁定する。業務上の可否は Model が定義した判定を使う。 |
| Effect の実行層 | 受理された処理を実行し、成功・想定内エラー・defect・中断を区別して境界へ返す。 |
| View | Model の判定と UI 状態から作られた操作可否を表示し、要求を送る。表示用の数値整形などは局所で行ってよい。 |

一覧取得とキャンセル操作は別の状態でよい。Atom を使う場合も、一覧の再取得が進行中のキャンセル状態をリセットしない構成にする。キャンセル成功後の一覧更新は採用済みのキャッシュ無効化・再取得機構に接続する。

同じ注文への試行 A を取り消して試行 B を始めた後、A の応答が届く例を確認する。注文 ID だけでは A と B を区別できない。実行層が保証する結果除外を使うか、必要なら操作 ID で照合し、A の成功も失敗も B の状態や表示へ混入させない。通信中断だけでサーバー上のキャンセルが取り消されたとは判断しない。

## 例2: フォーム送信

フォームライブラリは入力値と形式チェックを保持する。検証済み入力を送信要求として Mediator へ渡し、業務規則は Model／ユースケースで検証する。

取得・送信の状態だけで必要な UI を表せる場合は、その状態を共用する。Atom の AsyncResult を使う場合も、表示のためだけの別 reducer や `isSubmitting` を追加しない。前回の結果を保持しながら処理中になる仕組みでは、再試行中と前回の失敗・成功を区別して表示する。

送信中の閉じる操作が取消を意味するなら、Mediator の遷移として扱う。フォームの送信状態と業務フローの進行状態は、開始・完了・取消まで同じ責務を表すと確認できる場合だけ共用する。名前が似ていることだけで同一視しない。

## 例3: 音声入力と範囲選択の排他

両フローが同時に動けない場合、共通の親 Mediator が現在の所有者と切替方針を管理する。子は自分のフローを扱い、開始要求など自分だけでは決められないイベントを親へ委ねる。View 間で相手を停止させない。

切替に終了待ちが必要なら、その待機も状態として表し、停止要求を送っただけで次のフローを開始しない。Effect の実行層が中断と解放を行い、必要な終了結果を親へ返す。独立して動けるフローのために、この排他用の親を追加する必要はない。

## Effect を使う実行境界

Model／ユースケースでは Effect を合成し、実行は既存のアプリケーション境界や UI バインディングに任せる。各 View が個別に実行 runtime を作る構成を避ける。ROP の具体的な記法は `rop` スキル自身の `references/effect-ts.md` を読む。

想定内の業務エラーは型付きエラーとして扱い、defect や中断を同じ業務エラーに潰さない。UI 境界で必要な通知・観測へ接続する。[公式: Expected Errors](https://effect.website/docs/v4/error-management/expected-errors)

処理の中断は Fiber、リソースの寿命と解放は Scope の役割を踏まえて構成する。Scope を閉じることだけで任意の実行が中断されると仮定せず、タスクと所有者の寿命を導入版の仕組みで結び付ける。Mediator が決めた取消方針をここで実行し、同じ判断のために別のキャンセルフラグや自作 scheduler を重ねない。[公式: Concurrency](https://effect.website/docs/v4/concurrency/basic-concurrency)、[公式: Scope](https://effect.website/docs/v4/resource-management/scope)

## 実装時の検証

変更した責務の境界で、該当する振る舞いを確認する。

| シナリオ | 期待する結果 |
| --- | --- |
| 既存の TanStack Query 画面の小修正 | 既存設計を保ち、Effect／Atom の導入を要求しない。 |
| 複数 View が Context を読む | 購読は共有でき、操作の裁定は同じ所有者へ届く。 |
| 発送済み注文をキャンセル | Model が実行時に拒否し、UI はその結果を表示する。 |
| 同じ注文で取消後に再試行 | 前の試行の成功・失敗が新しい試行へ混入しない。 |
| 失敗後にフォームを再送信 | 前回の失敗と現在の送信中を区別する。 |
| 音声入力中に範囲選択を要求 | 親が切替を裁定し、必要な終了・解放を待つ。 |
| ツールチップを閉じる | 局所表示だけが変わり、業務フローには介入しない。 |
