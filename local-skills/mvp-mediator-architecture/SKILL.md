# MVP + Mediator Architecture

## 適用範囲と進め方

UI の責務分離を設計・レビューする。新規開発では以下の分担を出発点にし、既存プロジェクトではその規約と変更範囲を優先する。各パターンは必要な問題にだけ適用する。名称を揃えるためのクラス・層・ストアや、小修正を契機とした移行は不要。

1. **既存の所有者を確認する**: 業務規則、取得・送信状態、操作識別、取消、実行と寿命をどこが持ち、どの保証が既にあるかを確認する。対象の設計に React／TanStack／Effect が含まれる場合（設計メモ・抽象モデルも含む）は [実装への当てはめ](references/tanstack-effect.md) を読む。
2. **操作間の制約を特定する**: 業務上の可否と、UI の連打・切替・取消・結果採用の方針を分ける。既存機構で満たす部分を共用し、不足する制約だけを追加する。
3. **必要な判断を一つの所有者へ置く**: 独立したフローは独立に保ち、競合するフローだけを共通の親で調整する。既存の関数や binding がこの役割を果たすなら、そのまま使う。
4. **保持状態を説明する**: 追加・保持する状態は下記「状態は既存機構から導出する」の表で説明する。実装・抽象モデルを作る前の整理を推奨するが、記入の順序は完了条件に含めない。提案のみの場合も、提案で保持する状態を説明する。

## 成果物と完了条件

設計提案だけなら、操作方針と具体的な確認ケースを示し、未実行を明記する。実装では既存プロジェクトの検証方法を使う。表示変更のために抽象モデルや状態機械を作らない。

制約のあるフローを実装した場合、または抽象実行モデルを求められた場合は、次の形で検証する。関数名は既存コードに合わせてよい。

- **通常経路**: self-check の最初に、新しい初期状態から開始要求と現在の処理の正常完了だけを与える独立した `normalPath` を実行する。失敗・反復要求・古い通知は別の名前付きケースにする。操作方針から定めた後状態・資源所有者・実行効果のうち関係する値を assertion で照合する。
- **純粋な遷移**: 純粋なモデルでは状態を引数から受け、新しい状態を返す。ケース内の検査対象遷移では、次の順序で各呼出し直後の入力不変性、初回結果の保持、同入力の結果一致を assertion で確認する。比較対象は入力 state と、effects を含む全返却値。外部 I/O がないだけでは純粋とは扱わない。

  ```js
  const before = snapshot(state);
  const first = transition(state, event);
  assertEqual(state, before);
  const firstBefore = snapshot(first);
  const second = transition(state, event);
  assertEqual(state, before);
  assertEqual(first, firstBefore);
  assertEqual(second, firstBefore);
  ```

  これは比較順序の例であり、関数名やライブラリは既存コードに合わせる。`snapshot` は状態・返却値の意味を保持する独立した記録、`assertEqual` はその意味に合う等値比較を表す。通常のデータなら標準の複製・深い比較を使える。opaque や独自表現では意味を検査できる既存の方法へ置換し、空の外形だけを比べない。比較を用意できなければ未確認の範囲と必要な確認方法を記し、純粋性確認済みとしない。実アプリの状態表現を通常データへ制限したり、この検査のために汎用ライブラリや inspect API を追加したりする指定ではない。

- **導出表示**: binding の通常状態と追加の採用裁定をモデル化するときは、表示を `selectDisplay(bindingState, coordination)` のような読み取り関数から得る。完了通知は binding の結果と必要な裁定だけを更新し、Mediator 側で別の `display` を書き換えない。検査もこの読み取り関数の戻り値を照合する。

最終編集後、成果物を開いて次の順にメモを更新する。

1. **ケースと操作列を照合する**: 各ケースの実際の操作列を読み、上記の通常経路・別ケースの分担に対応付ける。検査追加後もこの分担が成立することを確認する。
2. **状態表を揃える**: 実際に保持する全フィールドへ表を対応付ける。追加・変更を反映し、モデル内の表現と本実装での情報源を別々の欄で照合する。
3. **assertionから根拠表を作る**: 最終コードを開き、assertionが照合する値、その値を得た操作、比較相手（期待値または比較対象）を拾って下表へ記録する。実行結果を対応付けた後、要件別の達成欄に実装箇所と根拠を示す。

| ケース | 観測時点 | 照合する値と期待値 | assertion の所在 | 実行結果 |
| --- | --- | --- | --- | --- |
| 名前付きケース | 値を得た操作の直後 | 対象値ごとの期待値・比較相手 | その値を照合する式または箇所 | 成功・失敗・未実行と、コマンド・結果の参照先 |

読みやすさのため観測時点ごとの行分割を推奨する。複数時点を一行にまとめる場合も、各時点の対象値・比較相手・assertion・実行結果を明確に対応付ける。同じ時点のstateとeffectsなど、各値の比較相手とassertionも個別に対応付ける。全assertionの転記は不要で、コマンド・出力は共通の参照先にまとめられる。

各検証主張の成功・失敗は、そのassertionを実行したケースの出力と終了結果で確定する。ケースの成功が裏付けるのは実際に照合した値だけ。要件上必要な検査が欠けていれば追加して実行する。それ以外の未確認事項も表に残し、assertionがなければ未実装、実行していなければ未実行と記す。成功・失敗・未実装・未実行が同じ行に混在する場合は対象ごとに区別し、区別できなければ行を分ける。

**根拠表の記入例**（検査コードの抜粋。名前やassertion形式は既存コードに合わせる。純粋性は前述の手順で別途確認する）:

```js
const stale = transition(pending, oldCompletion);
assert.deepEqual(stale.state, pending);
assert.deepEqual(stale.effects, []);
const current = transition(stale.state, currentCompletion);
assert.deepEqual(observe(current.state), expectedCurrent);
```

| ケース | 観測時点 | 照合する値と期待値 | assertion の所在 | 実行結果 |
| --- | --- | --- | --- | --- |
| completionCheck | 旧通知直後 | stale.stateはpendingと同値、stale.effectsは空配列 | stale.stateとstale.effectsのdeepEqual | 実際のケース結果への参照 |
| completionCheck | 現通知直後 | observe(current.state)はexpectedCurrentと同値 | observe(current.state)のdeepEqual | 実際のケース結果への参照。current.effectsの検査は未実装 |

この例は推奨する行分割を示す。旧通知と現通知を一行にまとめても、各値の比較相手・assertion・実行結果とcurrent.effectsの未実装を区別できればよい。例の実行結果欄は実測後に埋める。旧通知直後の報告は「state維持、effects空」とし、それぞれの比較相手を保つ。現通知直後のeffectsを確認するにはcurrent.effectsのassertionが必要で、stale.effectsの検査では補えない。

実行検査の説明は表へ集約し、達成欄から対応行を参照することを推奨する。正確な要約・重複は許容し、表外の検証主張も同じ観測値・比較相手・実行結果へ対応付ける。コード読解による確認、実アプリ統合、抽象モデルの検査は区別する。提案のみの場合は、具体的な操作列・状態・確認ケース・期待値を示し、assertionと実行結果は未実装／未実行とする。

実装を修正した場合は影響する検査を実行し直し、表も更新する。提案のみの完了条件は成果物とメモの対応が揃うこと、実装の完了条件はそれに加えて必要な検査が成功することとする。

確認する境界は、業務の実行時検証、状態の再利用、同じ対象への再試行と古い応答、必要な終了・解放、局所表示の独立性。今回の変更に関係するものを選ぶ。

## 責務の所有者

| 役割 | 所有する責務 |
| --- | --- |
| Model／ユースケース | 業務概念・不変条件・業務規則と実行時の検証。React・Atom から独立した処理。 |
| Mediator | UI フローの操作許可、状態遷移、取消・再試行の方針、結果採用。Model の判定や結果を表示へ変換する。 |
| 実行層 | 裁定された処理の実行、通信中断、購読解除、リソース解放。Effect 採用時はその合成・Fiber・Scope を使う。 |
| UI binding | 実行状態と React の接続。採用済みの Atom 等が持つ pending／result と購読機構を共用する。 |
| View | 表示と利用者操作の通知。他の操作の許可・取消・進行に影響しない局所状態。 |

これは役割の区分であり、各行に別モジュールを作る指定ではない。Mediator は判断の役割で、純粋な関数と既存 binding の組合せでもよい。専用 class、store、reducer を必須にしない。

例えば発送済み注文の取消可否は Model／ユースケースが実行時にも検証する。UI はその判定と進行中の状態から表示を作る。disabled のために業務規則を再実装しない。

## 状態は既存機構から導出する

既存の取得・送信状態だけでフローを表せるなら、その状態を使う。既存 binding の操作識別や結果除外が方針を満たすか確認し、満たすなら同じ操作 ID や pending／result を別途保持しない。追加の結果採用が必要なら、例えば採用する操作 ID だけを持ち、その操作の表示値は binding から導出する。排他や解放待ちなど、追加制約がある場合にだけその状態を表す。

追加・保持する状態は、メモの「状態の説明」欄に次の形で列挙する。同じ目的・所有者・取得元の状態は一行にまとめてよい。

| 状態 | 判断に使う目的・所有者 | 抽象モデルでの区分 | 抽象モデルでの表現 | 本実装での情報源 |
| --- | --- | --- | --- | --- |
| 実際に保持するフィールド | 何を決め、誰が持つか | 既存 binding／実行層の模擬・追加の裁定・View の局所状態・検証専用の補助のいずれか | モデル内の保存場所・表現 | 既存機構の値、追加する所有者、未確認＋具体的な確認対象、または検証専用のため不要 |

実装では抽象モデル専用の2欄を省略してよい。抽象モデルでは、採番や進行段階も含む全保持フィールドについて、モデル内の表現と本実装の情報源が別々に説明されれば完了とする。例えば `state.id` はモデル内の表現であり、情報源が未確認なら「既存の実行境界が返す操作IDを確認する」と記す。「未確認＋確認対象」は説明完了として扱い、実装への接続が検証済みであることとは区別する。**本実装の判断でも必要な情報は検証専用ではない**。検査用の採番やログを本実装の状態として増やさない。

## View と接続方法

このスキルは、購読と局所的な表示状態を許す実用上の Passive View を採用する。Model との直接の接続をなくす厳密な Passive View とは区別する。厳密さが必要なプロジェクトでは、Atom 等を読む接続部分と、props とイベントだけを扱う表示部分を分ける。[Passive View の原典](https://martinfowler.com/eaaDev/PassiveScreen.html)

props、Context、compound components はプロジェクトに合わせて選ぶ。複数の View が表示状態を購読したり同じイベント送信口を使ったりしてよい。購読の個数によらず同じ判断を同じ所有者へ届ける。転送専用コンポーネントは不要。

表示整形・表示条件の分岐・tooltip の開閉は View に置ける。入力値と形式チェックはフォームが保持できる。他の操作の許可・取消・進行を変える判断は担当の UI 裁定へ渡す。閉じると送信を取り消すダイアログは、単なる表示の開閉ではない。View に業務規則を置いたり、兄弟 View を直接操作したりしない。

## 必要な範囲の階層と Chain of Responsibility

複数フローが競合するときは、共通の親が切替を裁定する。各担当が自分の範囲で処理し、範囲を超える要求だけを親へ委ねる。これが CoR の適用箇所。処理済みの要求をさらに親で実行して二重処理にしない。単純な UI にイベント転送チェーンを追加しない。

Root は既存の組立箇所を使い、必要なら全体に関係する UI 操作を裁定する。「唯一の裁定者」は同じ判断の所有者が一つという意味で、全イベントを一つの global FSM に集める意味ではない。独立した注文一覧とプロフィール編集は独立に保てる。

## 状態遷移と非同期処理

状態間の制約があるフローでは、状態・イベント・許可される遷移を明示する。reduce を使うなら同期・純粋に保ち、実行は境界へ委ね、I/O の結果をイベントとして戻す。同じ許可条件を呼出側にも重複させない。

再送信・取消・結果採用の方針は担当の UI 裁定が所有する。方針に従う通信中断・購読解除は実行層へ委ねる。ライフサイクルの cleanup と業務判断を区別する。中断は外部処理の巻戻しを保証しない。

古い成功・失敗やキャッシュ再検証で進行中の操作を上書きさせない。同じ対象への再試行を区別する場合は、ドメイン ID だけでなく操作の識別を使う。単なる再描画は購読へ任せ、操作の許可・進行を変える通知は裁定へ戻す。結果除外の実装箇所は既存機構の保証に合わせる。

新しい要求の意図と、継続中の実行の識別を分ける。待機先を更新しても、実行中の停止・解放の ID と必要な完了通知は維持する。表示へ採用しない結果でも、所有資源の解放や次の開始に必要な終了通知は処理する。停止要求を送っただけで次を開始せず、必要な終了・解放を待つ。

## 他の設計規約・Effect との分担

- **ドメインモデリング／ヘキサゴナル**: 業務の型・規則と UI 接続を分ける。必要な外部依存の Port は Effect の Service、実装の供給は Layer で表せる。すべての関数を Service に包む必要はない。
- **VSA**: 機能・ユースケース単位の slice を維持し、その中に必要な UI 裁定を置く。
- **ROP**: Effect 採用時は成功値・型付きエラーの合成として使う。常に別の Result を重ねる必要はない。具体的な成功・失敗の合成を実装するときは `rop` スキルと該当言語の reference を読む。
- **DAG**: モジュール、Service／Layer 構築、派生状態の依存に循環を作らない。再試行など時間上の状態遷移には循環があってよい。イベント通知の方向と import の依存を区別し、親への通知口は引数や Context 等から供給する。専用 DAG scheduler は不要。
- **Effect**: 純粋な業務判定と Effect の記述を合成し、既存の境界で実行する。型付きエラー、明示した依存、Fiber／Scope による実行と寿命を優先し、想定内エラー・defect・中断を区別する。CoR や Mediator のために同等の非同期機構を自作しない。
